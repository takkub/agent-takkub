### 1.2 PermissionEngine rewire

**Where:** `src/agent_takkub/core/capabilities/permission_engine.py`. The class exists and is fully
built — `mcp_allowed()` (line 54) and `evaluate_shell_command()` (line 61) both delegate to the
exact same live functions (`pane_tools_policy.effective_mcps`, `pane_guard.classify`) the current
hot path already calls, plus audit logging on denial (lines 74-84). Its own module docstring says
outright (lines 35-39): *"Not yet wired into `cli.cmd_guard` itself (the live `takkub _guard` hook
still calls `pane_guard.classify` directly) — rewiring that hot path belongs to whichever phase
actually replaces the caller, so it can be proven behavior-neutral under the full suite first."*

Confirmed live: `cli.py:1954` `cmd_guard` — the actual `PreToolUse`/`Bash` hook fired on **every**
Bash call from every claude-provider pane — imports `pane_guard` directly (`cli.py:1969`) and
never touches `PermissionEngine`.

**What's left to do:** change `cmd_guard` (`cli.py:1954-` ) to call
`PermissionEngine().evaluate_shell_command(command, role, ...)` instead of
`pane_guard.classify(command, role)` directly, and verify the audit-logging side effect
(`log_capability_event` on every DENIED verdict) doesn't change `cmd_guard`'s own behavior
contract ("Never raises. Any unexpected failure allows the command (exit 0)" — `cli.py:1965-1967`).
This is a **single hot-path caller swap**, but that hot path fires on every Bash call from every
active pane on the user's live cockpit — a regression here doesn't just break a feature, it either
(a) fails open and silently disables the shell guard for every pane, or (b) fails closed and wedges
every pane's shell mid-task. Both are bad; (b) is worse because it's loud but blocks work, (a) is
worse because it's silent.

**Owner:** backend.
**Depends on:** nothing structurally — `PermissionEngine` is already complete — but this is the
**one gap that changes behavior on the user's live cockpit today**, not just adds new dead code.
Needs full-suite gate (not targeted) before merge, per the project's own test-tier rule, plus a
manual smoke: trigger one known-denied command (e.g. the `npx playwright` case the module
docstring itself cites) through the real hook path, not just the unit test mock.
**Risk: highest of the four** — see §4.

### 1.3 Model registry

**Status (2026-08-23): store skeleton done, resolver wiring still open — see below.**
The store landed at `core/model_catalog/` (`registry.py` + `legacy.py`), **not**
`core/models/registry.py` as this section originally said — that location is
unreachable: `pyproject.toml`'s `core-models-pure` import-linter contract forbids
`agent_takkub.core.models.*` from importing `agent_takkub.core.storage` at all ("a model
must never depend on how it gets persisted"), and a JSONL store must import
`core.storage.jsonl_store` + `core.storage.paths`. `core/model_catalog/` plays the same role
for models that `core/accounts/` already plays for accounts — `core.models.model` stays pure
vocabulary (unchanged), `core.model_catalog.registry` is the storage layer on top of it, and
`core.model_catalog.legacy` reads ladder-step-1's wrapped `models/registry.json` /
`models/aliases.json` blobs into real `ModelDefinition`/`ModelProfile` objects (fail-open:
missing/corrupt/empty data all read as `[]`, same as `core.storage.legacy_reader.read_json`).
Tested against fixtures only (`tests/test_core_model_catalog.py`) — real data still needs
`migrate apply` to have run at least once, per this section's own dependency note below.
`ModelDefinition.id` from the legacy reader is the composite `f"{provider_id}:{model_id}"`, not the
bare model id — `provider-models.json` legitimately lets two providers select the same model
(e.g. claude and cursor both on `claude-sonnet-5`), and the registry is an upsert log keyed by
`id`, so a bare model id made the second provider's entry silently overwrite the first
(`for_provider("claude")` then returned `[]` for a provider that *did* have a model). Same
silent-data-loss class as #340/#341/#346/#350. `name` stays the bare model id.

**Not done yet:** wiring a resolver into `core/routing/` — deliberately out of scope for this
pass (Wave C, gated on `migrate apply` per §3 below), and the account-scoped model override
design question (`REUSE_VS_REWRITE_MATRIX.md:46`) is still open.

**Where:** `src/agent_takkub/core/models/model.py`. `ModelDefinition` (line 12) and `ModelProfile`
(line 27) are `@dataclass(frozen=True, slots=True)` — **pure vocabulary, Phase 1 output, exactly as
labeled**. The module docstring says it outright (lines 1-4): *"NEW: today `provider_models.py`
only tracks per-role model selection, not a model registry."*

Grepped the entire `src/` tree for `ModelDefinition(` / `ModelProfile(` (actual construction, not
just the class definitions) — **zero matches anywhere.** No `core/models_registry/` or
`core/models/registry.py` package exists at all — contrast with `core/accounts/` which has a full
`registry.py` (JSONL-backed) + `selector.py` + `facade.py` + `switch_log.py`. The account layer
that Phase 2/3 built is the template this gap is missing; the model layer stopped at "define the
shape" and never got the "build the store" step.

Live system today is still 100% `provider_models.py` (per-role string → model id) and
`role_models.py`, migrated as an inert JSON blob copy by ladder step 1
(`RegistryCopyStep`, `phase8b-report.md` §8b-2 row 1: `provider-models.json`/`role-models.json` →
`models/registry.json`/`models/aliases.json`, wrapped verbatim, not reshaped). Settings UI's
Overview page (`settings_core_v2.py`, phase 9) reads `core.versioning.store` and
`core.accounts.registry`, **never** `core.models` — there is no UI surface for this gap either.

**What's left to do:** an actual `core/models/registry.py` (JSONL store, same shape as
`core/accounts/registry.py`) that can load the ladder-step-1 wrapped blob
(`models/registry.json`'s `.data` field, same unwrap pattern `core.storage.legacy_reader`
already establishes per `phase8b-report.md` line 128) into real `ModelDefinition`/`ModelProfile`
objects, plus something that actually reads from it — most likely the routing layer
(`core/routing/facade.py`, `core/routing/router.py`) needs to gain a model-resolution step the
same way it already resolves provider/account. Matrix §2's own note is still unaddressed:
*"ข้อมูลเดิมต้อง migrate เป็น account-scoped model override"* (`REUSE_VS_REWRITE_MATRIX.md:46`) —
that's a real design decision (per-account model override), not just plumbing.

**Owner:** backend for the registry/store; whoever owns `core/routing/` (also backend, per the
matrix's ownership — no separate "model" role exists) for wiring a resolver in.
**Depends on:** ladder step 1 must have actually run (`apply()`) so `models/registry.json` exists
to read from — **this gap cannot be meaningfully finished before `migrate apply` runs at least
once**, though the registry *code* (empty-store case) can be built and tested against fixtures
first, same as every other `core/*` module has been.
**Risk: low** — additive, no existing caller depends on this being wired up, nothing regresses if
it ships incomplete. This is the safest of the four gaps to defer.

### 1.4 Claude argv extract

**Where:** `src/agent_takkub/core/providers/claude_adapter.py` + `plan.py`. Both files' docstrings

  (b) importing `spawn_engine` from core, which transitively pulls in PyQt6 ... trips the
  `core-is-bottom-layer` import-linter contract. Neither is acceptable this phase."*
- `plan.py:1-26` — the generic (non-claude) provider branch's argv assembly **was** successfully
  extracted (`assemble_generic_argv`, `plan.py:59-81`, verified byte-order-identical against
  `spawn_engine.py` lines ~1873-1977 by a golden-order test). The claude branch was deliberately
  **not** — `plan.py:21-25`: *"that is also why the ~800-line claude branch itself is not further
  split beyond the env hook: everything else in it is exactly this kind of Qt/PaneState-bound
  resolution."*

So `ClaudeCliAdapter.build_plan()` (`claude_adapter.py:55-74`) takes `argv` as a **caller-supplied**
parameter — it does not build claude's argv, it only turns an already-built argv + account into a
`SpawnPlan`. The actual ~800-line inline builder in `spawn_engine.py` (lines ~1990-2900) is
untouched and still the sole place claude's real argv gets assembled.

**What's left to do:** extract `spawn_engine.py`'s claude argv-building logic into something
`ClaudeCliAdapter` (or a new `core/providers/claude_plan.py`, mirroring `plan.py`'s
`assemble_generic_argv`) can call, without pulling PyQt6 into `core.*`. This means separating
*pure argv assembly* (order of flags, model/effort/mcp/project-scope/resume — same shape the
generic branch's extraction already did) from the *Qt/PaneState-bound resolution* that decides
*what* those flags' values are (token minting, agents.md rendering, `PaneState.model_override`
lookups) — the latter has to stay in `spawn_engine.py` and get passed in pre-resolved, exactly
the pattern `plan.py`'s own docstring lays out for the generic branch already. This is a genuine
~800-line refactor of the single most exercised code path in the app (bulk of the 8,501-test
suite per the most recent commit, `fb1872c`), against a branch explicitly marked
"ห้ามแก้ logic ใน branch เดิม" when Phase 3 looked at it.

**Owner:** backend, but this is the largest single gap of the four by code-touched, and the one
most likely to want a second pair of eyes / reviewer pass given `spawn_engine.py`'s test weight.
**Depends on:** nothing else in this plan — independent of migrate apply, ingest, or permission
rewire.
**Risk: medium-high** — not because the target behavior is unclear (the generic-branch extraction
already proved the pattern works), but because the source is ~800 lines of live, load-bearing,
Qt-coupled code that every claude-provider pane spawn goes through, and "prove behavior-neutral"
here means the full suite, not a targeted subset (matches the project's own test-tier rule: full
suite is the only tier that catches fake-signature-drift-style regressions in exactly this kind
of Qt-adjacent code).

## 2. แผนรัน `takkub migrate apply` จริงบน Windows

### 2.1 What actually happens today when you run it

`cmd_migrate` (`cli.py:1600-1642`) is a thin dispatcher — `apply` calls `MigrationEngine().apply()`
(`engine.py:64-71`), which walks the 8-step default ladder in order
(`engine.py:44-53`: `VersionMarkerStep` → `readonly-registries` → `role-agent` → `capability` →
`project` → `state` → `credential-reference` → `runtime-triage`) and **stops on the first step
whose `ok` is `False`** — this is not "best effort", it is stop-the-line by design
(`engine.py:8-11`). Every step shares one `MigrationJournal`/`BackupManager` pair
(`engine.py:39-53`), both rooted under `core_home()` (`journal.py:29`, `backup.py:21` —
**not** inside the new `StorageLayoutV2` tree being written to, an intentional separation since
the journal must survive independently of its own migration target).

Every step is copy-never-move (`phase8b-report.md` line 107-111): `apply()` only ever writes under
`StorageLayoutV2.root` (`DATA_HOME/v2/`, a deliberately separate namespace from V1's own
`projects/`/`runtime/`/`cache/` — `phase8b-report.md` §"Root placement decision", lines 51-58),
and always backs up its own prior V2 target before overwriting. **No V1 source file is ever
deleted or mutated by `apply`.**

### 2.2 What is genuinely new risk vs. what's already proven

- **Proven** (fixture tests, `tests/test_core_migration_v1_steps.py`): dry-run/apply/validate/rollback
  round-trip per step, unknown-field preservation, rollback restores prior value, credential step
  never writes a credential byte, worktree checkouts never copied, cache dirs never touched — all
  against **synthetic fixture V1 homes**, both `installed_merged` (`SETTINGS_HOME == DATA_HOME`,
  mirrors real `~/.agent-takkub`) and `dev_split` (`~/.takkub`) shapes.
- **Not proven**: `apply()` against this machine's **actual, currently-in-daily-use**
  `~/.agent-takkub`/`~/.takkub`. Phase 8b's own dry-run (`phase8b-report.md` §8b-4) is the closest
  rehearsal — it ran read-only against the real `SETTINGS_HOME` on this exact machine and every
  step reported `ok: true` with concrete counts (5/5 registries, 2/2 capability files, 4/4 state
  files, 1 credential-reference resolvable) — but a dry-run proves the *read* path, not the
  *write-then-survive-a-real-restart* path.

### 2.3 Proposed apply sequence (Windows)

1. **Pre-flight — do this before touching `apply` at all:**
   - `takkub doctor --storage-layout --json` → confirm `state: "v1"` (not `"mixed"` — a prior
     partial run would need `rollback` first, not another `apply`).
   - `takkub migrate inspect` then `takkub migrate plan` then `takkub migrate dry-run --json` on
     the **real** `SETTINGS_HOME`/`DATA_HOME` (not a worktree) — re-confirm every step still
     reports `ok: true` and the counts look sane (compare against the 2026-08-19 dry-run numbers
     in `phase8b-report.md` §8b-4 as a baseline; a big delta is a signal to stop and look, not to
     proceed).
   - **Manual backup outside the tool entirely**: copy `~/.agent-takkub` (or `~/.takkub` +
     the merged `DATA_HOME` if this machine is a dev checkout) to a separate location before
     running `apply` at all. The tool's own `BackupManager` only backs up *targets it's about to
     overwrite* (V2-side), not the V1 sources — belt-and-suspenders against a bug the fixture
     tests didn't happen to cover.
   - Close the cockpit (or at minimum, don't have panes actively writing to the files the ladder
     is about to read — `projects.json`, `.takkub_issues.json`, etc.) for the apply window, even
     though `apply` itself doesn't require the orchestrator socket (`cli.py:1601-1604`'s own
     docstring: "Pure-local ... works with the cockpit closed").
2. **Run `takkub migrate apply --json`.** Stop-the-line means a mid-ladder failure leaves earlier
   steps applied and later steps untouched — check `layout_state()` afterward
   (`layout.py`'s `layout_state()`, per `phase8b-report.md` lines 75-77) to confirm which state
   you're actually in (`v1`/`v2`/`mixed`).
3. **Run `takkub migrate validate`** immediately after — cross-checks V2 against the still-present
   V1 (V1 is never deleted, so validate has a live source of truth to diff against).
4. **Success criteria** (all must hold before calling this done):
   - every step in `apply`'s report has `ok: true`
   - `validate` reports `ok: true` for every step
   - `takkub doctor --storage-layout` reports `state: "mixed"` with 0 ladder steps remaining,
     and a `legacy-leftover` line explaining it. **`"mixed"` is the correct success state, not
     `"v2"`** (corrected 2026-08-22 after the first live rehearsal): the ladder is copy-never-move,
     so V1 is still present by design and `layout_state()` reports `mixed` for exactly that reason
     — `doctor` says so itself ("expected until the deprecation ladder (plan §2, Phase 10) removes
     V1; not itself a problem"). This criterion originally demanded `"v2"`, which the current
     design can never produce; following it literally would mean rolling back a migration that
     actually succeeded. `"v2"` only becomes reachable once Phase 10 removes V1.
   - the cockpit opens normally and a real spawn→assign→done round-trip works (the same smoke
     bar Phase 1's own Definition of Done used: `V2_IMPLEMENTATION_PLAN.md:159`)
   - re-run the **full** `takkub qa-gate` (not targeted) — the project's own rule for anything
     claiming behavior-neutral (root `CLAUDE.md`: full suite runs once at the qa batch gate)
5. **Rollback trigger**: any single `ok: false` in `apply`, `validate`, or the doctor check, OR
   any observed behavior change in daily cockpit use afterward → `takkub migrate rollback`
   immediately (walks the ladder in reverse, stops on first failure — `engine.py:82-89`), then
   stop and investigate before trying `apply` again. Do not attempt a second `apply` on top of a
   partially-rolled-back state without re-running `dry-run` first.

### 2.4 Does the phase8b "isolation" gap have to close first?

**No — verified not blocking.** The gap is: Core V2's own internal storage (`core_home()`'s
existing contents — `version.json`, the migration journal/backups themselves, `core/accounts`'
registry, the secrets store, conversation directories Phase 1-8a already write) is **not**
relocated by any of the 8 ladder steps (`phase8b-report.md` §"Gaps/follow-ups", first bullet,
lines 243-249). All 8 steps migrate *V1 config files* into `StorageLayoutV2`; none of them touch
Core V2's *own* already-running storage. `paths.py`'s legacy-fallback mechanism
(`core_home()`/`conversation_dir()`, `phase8b-report.md` §"paths.py's legacy fallback",
lines 79-103) exists and is tested, but currently always resolves to the pre-existing location
because nothing populates `StorageLayoutV2.system` yet — this is an **inert, documented
no-op today**, not a live inconsistency. Running `apply` does not make this worse: it's orthogonal
(the ladder never touches `core_home()`'s existing contents either way). It's a real gap that
should get its own future ladder step eventually (whoever writes it can reuse the fallback
already wired in `paths.py`), but it does not block this release's `apply`.

### 2.5 Windows-first, then Mac

Nothing in `engine.py`/`steps_v1.py`/`layout.py` is platform-conditional — every path operation
goes through `pathlib.Path` and `config.DATA_HOME`/`config.SETTINGS_HOME`, which already resolve
correctly on both platforms (per root `CLAUDE.md`'s cross-platform rule, and CI's own
windows-latest + macos-latest matrix gate). The **Windows-first** ordering in the epic isn't
about the migration code needing OS-specific work — it's about doing the live rehearsal on the
machine already in front of us (this one, `monch`'s Windows daily-driver cockpit) before touching
a second person's/machine's real data. Once `apply` has been run once on Windows and validated
clean, running it on macOS should be a repeat of §2.3 with no code changes expected — but it
still needs its own real dry-run + apply + validate pass on an actual Mac cockpit, not just "CI
is green on macos-latest" (CI never runs `apply` against a real user home, only fixtures).

## 4. ความเสี่ยงที่ควรกลัวที่สุด 3 อันดับ

### 1. `migrate apply` running against the user's real, daily-use prod cockpit
This machine's cockpit is not a throwaway test environment — the user works in it every day, and
by the epic's own account, the 5 `TAKKUB_V2_*` flags have been live in production since 1.0.84
with soak history that already surfaced 8 real bugs (#332-#339, epic checklist). `apply` is the
first ladder run against **real** `~/.agent-takkub`/`~/.takkub`, not fixtures. Copy-never-move
and per-step rollback (§2.1) bound the blast radius on the V2 write side, but they don't protect
against a step reading a real file in a shape the fixture tests didn't anticipate (the exact
failure mode `V2_IMPLEMENTATION_PLAN.md §4.2` point 1 already names as a project-wide lesson:
"ห้ามพิสูจน์ adapter ด้วย mock อย่างเดียว" — codex's 0.147 schema drift slipping past CI because
only `codex exec`'s old schema was tested, not the `codex-tui` shape actually used in panes).
**Mitigation:** §2.3's manual out-of-band backup (not just the tool's own `BackupManager`), close
the cockpit during the apply window, and treat step 4's full success-criteria list as non-negotiable
before calling it done — do not declare success on `apply`'s own `ok: true` alone without also
running `validate` and the doctor check.

### 2. Windows/macOS parity — Windows-clean does not guarantee Mac-clean
The migration code itself is platform-neutral (§2.5), but the *data on disk* is not:
`~/.agent-takkub`'s actual contents (which registries exist, whether `codex`/`opencode` config
dirs are present, whether custom roles were ever defined) can differ meaningfully between this
Windows machine and whatever Mac eventually runs `apply` — Phase 8b's own real dry-run already
shows this kind of environment-dependence (`0/0` for `project` and `runtime-triage` on this
worktree simply because those files/dirs don't exist here — `phase8b-report.md` §8b-4 table).
A clean Windows run proves the *code path* works; it does not prove the *Mac user's specific data
shape* will hit the same path with the same result. **Mitigation:** treat the Mac run as a full
repeat of §2.3, not a rubber-stamp — its own dry-run, its own backup, its own validate — and
budget for it being a separate person/session/machine (see §5), not something this session can
verify directly.

### 3. Non-claude providers silently degrading through gaps that were never fully closed
Multi-provider-first is a hard project rule (root `CLAUDE.md`). Two of the four gaps have an
honest chance of staying partially open past this release: kimi ingest (§1.1, genuinely unknown
scope) and the credential-reference step's `gemini`/`kimi`/`cursor` blind spot
(`phase8b-report.md` line 257-260, already tracked under #103, unrelated to but adjacent to this
release). Neither failure mode is loud — a provider that isn't ingested just silently has no
conversation history in V2, and `apply`'s ladder reports `ok: true` regardless (credential-
reference step 6 already handles "no confirmed isolation knob" as a correct no-op, not an error —
`registry_copy_step`/`steps_v1.py` design intent, §1.1 table). **Mitigation:** the doctor/validate
output after `apply` should be checked for these providers specifically, not just "did every step
say ok" — and the kimi ingest decision (§1.1, build vs. document-as-unsupported) should be made
explicitly rather than left implicit, so it shows up in a report the same way `supports_remote_history=False`
shows up honestly today rather than silently.

## 5. สิ่งที่ยังตอบไม่ได้ / ต้องถาม user

1. **Scheduling the Wave B apply rehearsal**: this needs a window where the user's cockpit can be
   closed/quiet on this machine, and the user should decide when that is (not a pane deciding
   unilaterally to run `apply` against their daily-driver environment). Also worth asking: is
   there a spare/less-critical Windows environment to rehearse on first, or does the real cockpit
   have to be the first live run?
2. **Mac execution**: this session has no macOS access. Who runs the Mac leg — the user personally,
   a separate agent session with Mac access, or does the user want to defer Mac entirely for a
   later release? The plan assumes it happens (epic says "Windows ก่อน แล้ว Mac"), but the *how*
   (whose machine, whose hands) isn't answered by anything in the repo.
3. **Kimi ingest scope decision** (§1.1): once investigated, if kimi turns out to have no
   accessible local transcript store at all, is "kimi stays unsupported for ingest, same as its
   existing `supports_remote_history=False` posture" an acceptable close for this gap, or does
   the epic consider that not-actually-closed? Worth deciding before the investigation, not after,
   so the investigator knows what "done" looks like.
4. **PermissionEngine rewire timing** (§1.2, Wave C): this plan deliberately sequences it after
   the apply rehearsal to isolate blast radius. Does the user agree, or is there a reason it needs
   to land earlier (e.g. a known security gap being actively exploited, which nothing in the repo
   suggests, but this plan can't rule out from code alone)?
5. **Whether the phase8b "own storage not relocated" gap (§2.4) needs a tracked GitHub issue**
   before 2.0.0 ships, or can stay a documented-but-unscheduled gap in `phase8b-report.md`
   indefinitely. This plan concluded it doesn't block `apply`, but "doesn't block" isn't the same
   as "user is fine leaving it open with no tracking."
6. **What actually counts as 2.0.0 being "done"** — the epic checklist's last line bundles apply +
   4 gaps into one checkbox. Does the user want one PR/release per wave (as this plan proposes),
   or is 2.0.0 meant to ship as a single bundled cut once everything above is green? Affects how
   Lead should sequence the waves against release tagging.
