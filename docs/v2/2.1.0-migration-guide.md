# Migration guide — 1.x → 2.0.x → 2.1.0

Status: release preparation, reviewed against `60abb771` on 2026-09-10. **Do not deploy this candidate:** [Round 2 acceptance](../audit/2026-09-10-504-acceptance-review.md#round-2--60abb771) is FAIL. Use the procedure below only after the fixes and release gates recorded there are complete.

## Upgrade

1. Record the installation's actual `DATA_HOME`. Close every cockpit and agent pane using it, and take a complete backup outside that directory, including archives and provider data. Keep the original backup throughout the upgrade and downgrade window.
2. If running 1.x, install a supported 2.0.x release with the installation's existing package manager. Start it once, let migration finish, then run `takkub migrate validate` and `takkub doctor --storage-layout`. Verify projects, named accounts, custom roles, provider/model settings and actual provider access. A V1 tree plus nested `v2/` is expected at this stage. Do not jump directly from 1.x to 2.1.0.
3. Close 2.0.x and all panes, then install the approved 2.1.0 release. Use the same data home. The first installed boot promotes the existing nested V2 contents, runs pending domain migrations, and archives selected retired V1 entries under `backups/v1-archive-<timestamp>/`. It removes the emptied live `v2/` directory. Provider homes and installation infrastructure must remain at their supported paths.
4. Run `takkub migrate validate`, `takkub doctor --storage-layout`, and `takkub migrate restore-v1 --list --json`. Compare retired V1 files with the archives using pre-upgrade counts and checksums. Account separately for unchanged provider/infrastructure files and promoted V2 targets, allowing only the explicitly retired junk (`openviking/`, `claude-config.partial/`, `.takkub_issues.synced-*.bak.json`) to be absent. Check every required live registry is readable and that projects, accounts, custom roles and model selections are still present. Test the providers you use before resuming work.
5. Keep all archive generations. There is no automatic archive expiry. Do not use `TAKKUB_V2_AUTHORITY=0` for recovery: it has been retired.

Fresh installed homes use the new domain directories from their first boot. Two empty-home boots at the reviewed commit create no root JSON or V1 archive. This does not imply all later settings/account operations have retired their old paths: `user-profiles.json` remains a live compatibility registry and is explicitly protected from archival.

Source/dev checkouts intentionally retain `DATA_HOME/v2/` and skip automatic migration to avoid collisions with repository folders. Do not force the installed migration over a checkout. The primary cockpit and worktree panes must resolve the same shared model/settings locations; H5 still violates this at `60abb771` and must be fixed before claiming dev acceptance.

## Restore before downgrade

**Keep 2.1.0 installed until restoration and verification finish. Never install/start 2.0.x against an unrestored 2.1.0 data directory.**

1. Close all cockpit instances and panes using the home. Back up the entire current 2.1.0 state separately. V1 archives are snapshots; edits made only in V2 after archival are not automatically converted back into those V1 snapshots. Preserve those edits and reconcile them before relying on an older version.
2. List generations without changing data:

   ```text
   takkub migrate restore-v1 --list --json
   ```

3. For a complete multi-generation restore, use:

   ```text
   takkub migrate restore-v1 --json
   ```

   This processes readable generations oldest first, then reverses promotion. If names overlap, the latest restored generation wins. To deliberately select a single generation, copy its exact `ts` value from the list:

   ```text
   takkub migrate restore-v1 --archive <timestamp> --json
   ```

   Supply only the timestamp, not the directory name or path. Selecting one generation does not restore files present only in other generations; it still runs the separate promotion rollback afterwards. Generations are not complete installation snapshots merely because they have a manifest.

4. Confirm every intended archive member exists and matches its manifest checksum before restoring, and compare the restored V1 inventory afterwards. At `60abb771`, restore skips missing members, copies corrupt members and can report success for an unknown timestamp. A green command alone is insufficient. Any missing/corrupt member or incomplete restore stops the downgrade; recover the archive from the separate backup and get the fixed candidate before proceeding.
5. Only after successful, complete restoration, install the intended 2.0.x release. Start it and repeat migration validation plus project/account/model/provider checks. The code review exercised a tagged 2.0.8 source round-trip in a separate Python process; a real old-wheel installation and authenticated provider checks still require release verification.

Archives are copied back and retained. Existing restore destinations are preserved through `BackupManager` under `DATA_HOME/runtime/core/migration_backups/<step-id>/<timestamp>/`. Keep these backups until verification finishes. The CLI does not offer a dedicated selector to recover a particular destination preimage. Do not treat generic `takkub migrate rollback`, which reverses the entire ladder, as an interchangeable downgrade command.

## Relocation and interruption

Schema 2 archive manifests use paths relative to their generation directory. When relocating, copy and independently verify the complete `backups/` tree, including `promote-v2-root-manifest.json`, into the intended data home before invoking the CLI against that home. Copy existing migration preimages separately if they are needed. The review tested relocation to another fixture directory, not a physical second drive. Do not assume old schema 1 manifests with absolute paths are portable.

At the reviewed candidate, the disk estimator counts `runtime/` and nested `v2/`, but omits archive-only payloads and destination preimages; manual apply/restore have no equivalent complete preflight. Ensure room on every affected volume for the archive, verified copies and preimages before using an approved build.

If migration is interrupted, stop further use and preserve the entire current home, including runtime migration records and backups. There is no guaranteed automatic resume or complete supported manual recovery after every interrupted transaction at `60abb771`. Do not blindly retry boot or alternate rollback/restore commands: a retry can replace the promotion inventory and make original paths unreachable through the restore command. The release review requires a durable recovery fix or an explicitly reviewed, tested replacement recovery procedure.
