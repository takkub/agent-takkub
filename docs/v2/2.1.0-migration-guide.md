# Migration guide — 1.x → 2.0.x → 2.1.0

Status: release preparation. `28a4e527` (Round 3, 2026-09-10) was FAIL — not releasable; `src/agent_takkub/core/migration/promote_v1.py` has since been refactored (transaction core rewrite, this candidate) to close the recorded blockers. Do not deploy without re-running [the acceptance harnesses](../audit/2026-09-10-504-acceptance-review.md) against this candidate's actual SHA first.

## How the transaction core works now

`PromoteV2RootStep`/`ArchiveV1LegacyStep` no longer share a single copy-then-conditionally-remove helper. Every move is now two independent phases per `apply()`/`rollback()` call:

1. **Copy phase** (`_copy_phase`) — copy-verify (sha256) every candidate into its destination. `src` is never touched. Any pre-existing destination is backed up first, so a merge into an already-populated directory (a live provider home, say) or a destination recreated since an earlier archive can always be undone byte-for-byte. A failure here undoes every destination this call touched and leaves every source untouched — a clean retry.
2. **Prune phase** (`_prune_phase`, promote/archive-apply and promote-rollback only — `ArchiveV1LegacyStep.rollback()`/`restore-v1` never prunes at all, since the archive itself is never deleted) — removes each entry's now-copy-verified source, one at a time, but only ever AFTER a durable ledger write naming that removal has itself succeeded. If the write or the removal fails for any entry, every entry THIS CALL already pruned (plus the one that just failed, in case its removal partially completed) is reconstructed file-by-file from its own already-verified destination — never a directory-level sweep of whatever else happens to live beside it. The whole batch is atomic: either every candidate in this call is fully promoted/archived, or none of them are.

Crash resume (a real process death, not a caught error) relies on the same file-level ledger: a resumed boot recomputes candidates from live V1 source state (never from the ledger), so a durable "this entry is committed" record written *before* its physical removal is enough — whichever side of that removal a crash lands on, the next run sees the correct state either way.

A multi-generation `restore-v1` (no `--archive`, every generation restored oldest-first) snapshots every name any selected generation could touch **once**, before the walk starts, into a command-level snapshot directory under the migration home. If a later generation's restore fails, every touched name is reverted to that single snapshot — never an intermediate generation's own overwrite (the earlier per-name "latest backup wins" model let a later generation's restore shadow an earlier one's backup for the same name, and never captured a name nested more than one path segment deep).

## Upgrade

1. Record the installation's actual `DATA_HOME`. Close every cockpit and agent pane using it, and take a complete backup outside that directory, including archives and provider data. Keep the original backup throughout the upgrade and downgrade window.
2. If running 1.x, install a supported 2.0.x release with the installation's existing package manager. Start it once, let migration finish, then run `takkub migrate validate` and `takkub doctor --storage-layout`. Verify projects, named accounts, custom roles, provider/model settings and actual provider access. A V1 tree plus nested `v2/` is expected at this stage. Do not jump directly from 1.x to 2.1.0.
3. Close 2.0.x and all panes, then install the approved 2.1.0 release. Use the same data home. The first installed boot promotes the existing nested V2 contents, runs pending domain migrations, and archives selected retired V1 entries under `backups/v1-archive-<timestamp>/`. It removes the emptied live `v2/` directory. Provider homes and installation infrastructure must remain at their supported paths. `takkub migrate apply`/`restore-v1` (and the automatic boot-time path) refuse to run at all when free disk space looks insufficient for the estimated copy — re-run once space is available rather than forcing it.
4. Run `takkub migrate validate`, `takkub doctor --storage-layout`, and `takkub migrate restore-v1 --list --json`. Compare retired V1 files with the archives using pre-upgrade counts and checksums. Account separately for unchanged provider/infrastructure files and promoted V2 targets, allowing only the explicitly retired junk (`openviking/`, `claude-config.partial/`, `.takkub_issues.synced-*.bak.json`) to be absent. Check every required live registry is readable and that projects, accounts, custom roles and model selections are still present. `validate()` now also rejects any archive generation whose `manifest.json` is missing or unreadable, and any promoted file that has since disappeared from its target — not just "nothing left to archive". Test the providers you use before resuming work.
5. Keep all archive generations. There is no automatic archive expiry. Do not use `TAKKUB_V2_AUTHORITY=0` for recovery: it has been retired.

Fresh installed homes use the new domain directories from their first boot. Two empty-home boots create no root JSON or V1 archive. This does not imply all later settings/account operations have retired their old paths: `user-profiles.json` remains a live compatibility registry and is explicitly protected from archival.

Source/dev checkouts intentionally retain `DATA_HOME/v2/` and skip automatic migration to avoid collisions with repository folders. Do not force the installed migration over a checkout. **Known open gap:** an explicit `TAKKUB_STORAGE_ROOT` override that disagrees with (or doesn't exist under) the primary cockpit's own derived root is still trusted verbatim by `core.storage.v2_target._primary_data_home()` — this is an existing, deliberately-tested contract (`tests/test_core_storage_v2_target.py`), not a regression from this candidate, and changing it requires an explicit policy decision (does an operator-supplied override ever get to override the cockpit, or never?) coordinated between backend and the storage-root owner before it can be tightened; do not hand-edit that override in production.

## Restore before downgrade

**Keep 2.1.0 installed until restoration and verification finish. Never install/start 2.0.x against an unrestored 2.1.0 data directory.**

1. Close all cockpit instances and panes using the home. Back up the entire current 2.1.0 state separately. V1 archives are snapshots; edits made only in V2 after archival are not automatically converted back into those V1 snapshots. Preserve those edits and reconcile them before relying on an older version.
2. List generations without changing data:

   ```text
   takkub migrate restore-v1 --list --json
   ```

3. For a complete multi-generation restore, use:

   ```text
   takkub migrate restore-v1 --json
   ```

   This processes readable generations oldest first, then reverses promotion. A snapshot of every name any selected generation could touch is taken once, before the walk starts — if a later generation's restore fails, every one of those names reverts to that snapshot (the state the command started from), not to whatever an earlier generation's own restore had just written. To deliberately select a single generation, copy its exact `ts` value from the list:

   ```text
   takkub migrate restore-v1 --archive <timestamp> --json
   ```

   Supply only the timestamp, not the directory name or path. Selecting one generation does not restore files present only in other generations; it still runs the separate promotion rollback afterwards. An unknown/typo'd timestamp is refused outright, not silently reported as success.
4. Every intended archive member's presence and checksum is verified against its manifest **before any destination is touched** — a missing or corrupt member refuses the whole restore for that generation rather than silently skipping just that file. Compare the restored V1 inventory afterward regardless. Any refused/incomplete restore stops the downgrade; recover the archive from the separate backup before proceeding.
5. Only after successful, complete restoration, install the intended 2.0.x release. Start it and repeat migration validation plus project/account/model/provider checks.

Archives are copied back and retained. Existing restore destinations are preserved through `BackupManager` under `DATA_HOME/runtime/core/migration_backups/<step-id>/<timestamp>/`, and the multi-generation command-level snapshot under `DATA_HOME/runtime/core/restore-v1-snapshots/<timestamp>/`. Keep these until verification finishes. Do not treat generic `takkub migrate rollback`, which reverses the entire ladder, as an interchangeable downgrade command.

## Relocation and interruption

Schema 2 archive manifests use paths relative to their generation directory. When relocating, copy and independently verify the complete `backups/` tree, including `promote-v2-root-manifest.json`, into the intended data home before invoking the CLI against that home. Copy existing migration preimages separately if they are needed. Do not assume old schema 1 manifests with absolute paths are portable.

The disk estimator counts `runtime/`, nested `v2/`, and archive/shared-dir-legacy candidates for `apply`; `restore-v1` uses a separate, more conservative estimate (the whole `backups/` tree) since its dominant cost is copying the archive back, not what a fresh promote/archive pass would move. Both the boot-time path and the manual `takkub migrate apply`/`restore-v1` CLI entry points now run this preflight and refuse to mutate storage when it fails — ensure room on every affected volume before using an approved build.

If migration is interrupted (a real process death, not a caught error), the next boot or manual `apply`/`restore-v1` call recomputes its candidates from live on-disk state and resumes safely: a source already removed in a prior run is simply not a candidate anymore, and the durable per-entry ledger record (written before each removal) means a resumed run never re-derives a promotion from a now-missing V1 source or silently drops an earlier interrupted run's ownership record. Preserve the entire current home, including runtime migration records and backups, until you've confirmed `takkub migrate validate` is green after the resumed boot.
