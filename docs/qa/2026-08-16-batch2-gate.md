## 4. Interaction ข้ามงาน (#144 busy-wait resend / #26 delivery-unconfirmed)

- **#255 TTL bump (30→120s) ไม่กระทบ #26's unconfirmed detection**: `unconfirmed=True` ถูกเซ็ตจาก path ของ `max_wait_ms`/`BUSY_WAIT_CEILING_SEC` (ready-poll timeout คนละตัวกับ delivery TTL) ไม่ได้ผูกกับ `delivery.expires_at` — คนละ gate กันจริง ตรวจโค้ดแล้วไม่มี dependency ไขว้
- **#255's TTL bump ไม่กระทบ resend window ของ #144**: TTL 120s ให้ margin เหนือ busy-resend budget ~90s (150×600ms) พอดีตามที่ commit อ้าง — ก่อนหน้านี้ TTL 30s < 90s worst-case ทำให้ resend ที่ landing หลัง 30s เสี่ยงโดน `_reject_stale`/`PtyWriter` ทิ้งทั้งที่ยัง valid อยู่ — นี่คือของเดิมที่ #255 ตั้งใจแก้ ไม่ใช่ regression ใหม่
- ⚠️ **Minor observation (ไม่ blocking)**: `TAKKUB_TASK_DELIVERY_TTL_SEC` env var **ชื่อเดียวกัน** ถูกใช้ซ้ำใน `lead_inbox.py` อีก 2 จุด (บรรทัด 2366, 2611 — `_pump_lead_notify`/force-deliver path สำหรับ **Lead's own notification queue**, คนละ subsystem จาก task-to-teammate delivery) ที่ยัง hardcode default `"30"` ไม่ได้ตามไปบัมพ์เป็น `"120"` เหมือน `task_delivery.py` เพราะ commit นี้ไม่ได้แตะจุดนั้น — ไม่ใช่ regression ของ 4 งานนี้ (ของเดิมเป็นแบบนี้อยู่แล้ว, ยังทำงานถูกต้องตาม design เดิมของมัน) แต่ถ้า operator ตั้ง env var นี้เอง (override) จะกระทบทั้ง 2 subsystem พร้อมกันโดยไม่รู้ตัว เพราะ **ชื่อ env var เดียวกันแต่ default literal ต่างกันคนละที่** — แนะนำแยกชื่อ env var หรือ sync default ให้ Lead พิจารณาเป็น follow-up (ไม่ blocking, ไม่มี evidence ว่าเคย mis-configure จริง)
