### a) `_pane_display_state()` splitting `"active"` → spawning/active/ready
Grepped every `== "active"` comparison in `src/` and `tests/`:
- `usage_meter.py:377` and `remote/static/app.js:2257,2370` compare **usage/limit status**, an unrelated field — not pane state.

- Dedicated regression tests exist: `tests/test_pane_display_state.py` (spawning/active/ready split, fail-open to `"active"` on exception).

Confirmed: no live code path anywhere compares `_pane_display_state()`'s return value against the literal `"active"` — Lead's prior finding holds.

### b) Spinner/terminal-init frames excluded from progress, real content counted
`pty_session.py` `_content_fingerprint()` strips spinner glyphs (braille block, dot/circle frames, isolated ascii `|/\-`) and trailing dots, drops blank rows, before comparing against `_last_content_fingerprint`. `_last_output_ts` (the progress clock used by `lead_inbox.py`'s busy-wait and the stall watchdog) is stamped **only** when the fingerprint changes — a redrawing spinner or terminal-init escape sequence (no visible glyph) does not bump it. `_last_byte_ts` (raw PTY liveness, unconditional on every byte chunk) is a separate, correctly-unfiltered signal used only for dead-vs-wedged-alive distinction (`seconds_since_byte()`), never fed into progress detection.

### c) Auth marker at ready prompt does not trigger blind delivery
`lead_inbox.py:1133-1148`: `_pane_ready_now = pane.session.is_at_ready_prompt()` is checked **before** the auth-marker branch; if ready, `auth_failure_streak` is reset to 0 and control falls through to the normal `ready_streak`/`_deliver()` path — the auth-failure branch (lines 1149+) is skipped entirely on a ready pane. "Ready wins" confirmed in code, matches the docstring comment at line 1138-1147.

### d) No-content watchdog capped at retry(1) + degrade(1) = 2 total
`lead_inbox.py:1210`: `if _no_content_attempts < 2: ... degrade=_no_content_attempts >= 1`. Counter is `PaneState.no_content_recover_attempts` (`spawn_engine.py:513`, default 0), incremented at `lead_inbox.py:1566` on each recovery attempt, and reset to 0 only on a confirmed-good respawn (`spawn_engine.py:1484`). Persisted on `PaneState` (survives the close()/respawn cycle that destroys the local closure), so the cap is enforced across the full retry→degrade sequence, not per-poll-loop. After both attempts are exhausted, falls through to the existing blind-deliver safety net (`elapsed[0] >= max_wait_ms`) — no infinite loop.
