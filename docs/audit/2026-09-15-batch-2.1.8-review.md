## HIGH

### H1 — `close()` on a role with a queued next-assignment always respawns it, even on an explicit user-requested close (#593 × close semantics)

`src/agent_takkub/orchestrator.py` — `close()` (~line 5421) and `_resume_after_close`/
`_dispatch_next_assignment` (~line 3090-3100).

```python
if (
    not suppress_pipeline
    and role_name != LEAD.name
    and (_task_undelivered_close or getattr(self, "_pending_assignments", {}).get(key))
):
    retained = _ps_close if _task_undelivered_close else None
    ...
    QTimer.singleShot(0, lambda: self._resume_after_close(project_ns, role_name, retained, closing_cwd))
```

`close()` has no way to distinguish "I'm closing this pane to make room for a replacement" from
"Lead explicitly asked to close this role and stop." Any non-empty `_pending_assignments[key]`
queue (built by #593's new busy-queue in `_assign_dispatch`, e.g. Lead ran `assign` twice while
the pane was still working on task 1) makes **every** `close()` call — including the plain one
`takkub close --role X` sends through `cli_server.py` with no suppress flags — schedule
`_resume_after_close` on the next event-loop tick. Since `retained` is `None` in this case (no
undelivered-task condition), `_resume_after_close` takes the `else` branch straight into
`_dispatch_next_assignment`, which calls `_assign_dispatch` with `current_pane is None` (just
closed) → **spawns a brand-new pane for the role and delivers the queued task**, seconds after
Lead told the system to close it.

This is not a hypothetical path — it is exactly what
`tests/test_orchestrator_done_gate.py:115` (`test_close_forwards_pending_assignment`) asserts:
a bare `orch.close("backend", project=...)` call (no `suppress_pipeline`) with a pending item in
`_pending_assignments` results in `_dispatch_next_assignment` firing and the pane coming back.
The test proves the *mechanism* works as coded; it does not distinguish "close to replace" from
"close to abandon", so it can't tell us whether this is the intended contract or an oversight
carried over from #593's design.

**Trigger:** `assign --role X "task1"` → (X still working) → `assign --role X "task2"` (queues
per #593) → `close --role X` (Lead wants to stop). Expected: X's pane goes away with nothing
running. Actual: a new X pane spawns automatically ~0ms later and starts task2.

**Suggested fix:** give an explicit user-initiated close a way to opt out — e.g. drop
`_pending_assignments[key]` before scheduling `_resume_after_close`, or add a `drop_queue=True`
default for the CLI's plain `close` path while keeping the auto-forward only for
replacement-driven closes (where `retained is not None`, i.e. the undelivered-task case).

## MEDIUM

### M1 — #605 "kept" migration targets have no fresh backup, so rollback can delete them instead of preserving them

`src/agent_takkub/core/migration/registry_copy_step.py` `RegistryCopyStep.apply()` (~line 132)
and `.rollback()` (~line 182); same pattern in `steps_v1.py`'s `RoleAgentMigrationStep.apply()`
(~337) / `.rollback()` (~420) and `ProjectMigrationStep.apply()`/`.rollback()` (~516, ~597).

When `source_retired()` is true, `apply()` intentionally skips `self.backups.backup(...)` for
that mapping — the whole point is "don't touch it, V1 is gone, the target already has the real
data" (see `registry_copy_step.py:74-90`'s own docstring: *"the target already has data" matters
just as much as "source gone"*). But every one of these steps' `rollback()` still does:

```python
backup = self.backups.latest_backup(key, target.name)
if backup is None:
    target.unlink(missing_ok=True)   # <-- deletes it
else:
    self.backups.restore(backup, target)
```

`latest_backup()` scans across *every* prior apply pass for that step, so in the common case
(target was written by a normal apply at some earlier point, which *did* back it up) rollback
still finds something to restore and this is a non-issue. The gap is narrow but real: any target
that has real data but was **never once backed up by this manager** (backup dir pruned/cleared
externally, or data seeded outside this migration step) — the exact "kept" mapping #605 was
written to protect — gets deleted outright on rollback instead of preserved. This directly
undercuts #605's own stated guarantee, specifically on the rollback path.

**Suggested fix:** in the "kept" branch, still call `self.backups.backup(...)` (a no-op copy of
the current, already-correct target) so rollback always has *something* to restore to, or make
rollback's `backup is None` case a no-op instead of a delete when the mapping's own
`source_retired()` is true.

### M2 — `_delete_candidates()` bypasses the protected-name check that `_archive_candidates()` applies

`src/agent_takkub/core/migration/promote_v1.py:2365-2374` (`_delete_candidates`), contrast with
`_archive_candidates()` (`:2428-2441`).

```python
def _delete_candidates(self) -> list[Path]:
    if not self.data_home.is_dir():
        return []
    out = []
    for p in sorted(self.data_home.iterdir()):
        if p.name in _DELETE_OUTRIGHT_NAMES or any(
            fnmatch.fnmatch(p.name, pat) for pat in _DELETE_OUTRIGHT_GLOBS
        ):
            out.append(p)
    return out
```

`_archive_candidates()` excludes anything in `_ARCHIVE_SKIP_NAMES | _named_account_home_names()
| _promoted_top_level_names()` before treating a top-level entry as safe to move — the whole
point of `_named_account_home_names()` (per its own docstring) is that a *named* account home
has no fixed basename a static list can enumerate, so it reads the live registry instead of
guessing. `_delete_candidates()` has no equivalent check at all: it matches purely on name/glob
and deletes unconditionally, including against the new #605 globs (`._*`, plus the exact names
`.DS_Store`/`.localized`/`Thumbs.db`/`desktop.ini`). A registered named-account home (or any
real top-level entry) whose basename happens to collide with one of those exact junk names, or
match `._*`, is deleted outright with no protection check and no way to recover it via the
archive path.

This is the case Lead specifically asked to verify ("junk `._*` glob ไม่จับไฟล์จริงชื่อขึ้นต้น
`._`") — confirmed: the code has no name-collision guard for `_delete_candidates()` at all, only
for `_archive_candidates()`. Low likelihood (requires a user's own path to literally collide with
a junk name), but the asymmetry with the sibling method is real and easy to close.

**Suggested fix:** filter `_delete_candidates()` through the same `protected` set
`_archive_candidates()` computes (`_ARCHIVE_SKIP_NAMES | _named_account_home_names() |
_promoted_top_level_names()`).

### M3 — a re-queued item can lose its FIFO position

`src/agent_takkub/orchestrator.py` `_dispatch_next_assignment` (~3055) / `_assign_dispatch`'s
busy-check (~3125-3159).

`_dispatch_next_assignment` does `item = queue.pop(0)` (removes from the front) then calls
`self._assign_dispatch(**item)`. If `_assign_dispatch`'s own busy-check still finds the pane
occupied at that instant (`current_pane is not None and current_pane.state not in
("done","empty","exited")`), it re-queues the item — but via `self._pending_assignments
.setdefault(key, []).append(...)`, i.e. onto the **end** of the list, not back at position 0.
`_dispatch_next_assignment`'s own `if not ok: queue.insert(0, item)` only fires on an actual
failure (`ok is False`); the busy-requeue path returns `ok=True` ("queued after current task"),
so nothing restores the original front position. With two or more items already queued, this
silently reorders them: `[A, B, C]` → dispatch `A` (still busy) → becomes `[B, C, A]`.

The `pending_state.task_id != had_task_id` guard placed just before the
`_dispatch_next_assignment` call in `done()`'s finalize path narrows the window (it bails if the
pane's active task already changed), so this is not proven to reproduce today — flagging as a
real but unconfirmed race for anyone touching this path next.

## LOW

### L1 — mint-before-bind race can revoke a not-yet-bound legitimate pane token (#594)

`src/agent_takkub/spawn_engine.py` `_mint_pane_token` (~1563-1606). The revoke-on-mint loop only
spares an old token for the same `(project_ns, role_name)` pair when it is **already bound**
(`bindings.get(old_tok)` not None) **and alive**:

```python
bound_session = bindings.get(old_tok)
if bound_session is not None and bound_session.is_alive:
    continue
```

A token minted moments earlier for the same pair but not yet bound (spawn still mid-flight,
before `_launch_session`/the claude branch reaches its `self._bind_pane_token(pane_tok,
session)` call) has `bindings.get(old_tok) is None` → gets revoked by a second, concurrent mint
for that same pair. When the first spawn later reaches its own bind call, it's binding an
already-revoked token — that pane's own auth would then fail. The class docstring claims the
"successor side of a replacement spawn's mint-before-bind race... must survive" but the guard
only covers the *already-bound* half of that race, not the *not-yet-bound* half.

Likely unreachable today: `spawn()` runs synchronously on the Qt main thread with no
`await`/`processEvents()` between mint and bind in any of the three paths (shell/provider/claude)
I traced, so two `spawn()` calls for the same `(project, role)` can't actually interleave under
the current event-loop model. Flagging so it isn't reintroduced if that assumption changes (e.g.
an `await` or explicit event-pump gets added somewhere in that stretch).

### L2 — `close --role reviewer` picks one of `qa`/`critic`, not both, when both are alive

`src/agent_takkub/orchestrator.py` `resolve_pane_role` (~2051), chain order from
`routing_planner.pane_role_resolution_chain`: `["reviewer", "qa", "critic"]`. If a project has
both a legacy `qa` pane and a legacy `critic` pane alive at once, any single-target command using
the generic `reviewer` name (`close --role reviewer`, `send --to reviewer`, `task show --role
reviewer`, …) always resolves to `qa` (first match in the fixed chain) — `critic` is left running
and untouched, with no indication to the caller that a second pane under the same "reviewer"
umbrella still exists. Edge case limited to mixed legacy usage during the #513 transition period,
not a security concern, but worth a doc/UX note (e.g. `close --role reviewer` warning when more
than one candidate is currently alive).

### L3 — `_turbo_force_args` misses `npx turbo ...` / `pnpm exec turbo ...` forms

`src/agent_takkub/verify.py:199-221`. Detection is "first shell-segment's first word is
literally `turbo`":

```python
uses_turbo = any(seg.split(None, 1)[0:1] == ["turbo"] for seg in segments)
```

A `verify`/`test` script written as `"npx turbo run test"` or `"pnpm exec turbo run test"` won't
match, so #600's original problem (a turbo cache-hit replaying only `PASS 58.7s` with no
underlying test-runner summary, leaving qa-gate's log with no evidence a real run happened) can
still slip through for those forms. Lead flagged this and asked for an easy fix if there is one —
there is: also match when the first word is a known runner (`npx`/`pnpm`/`yarn`) **and** `turbo`
appears as the very next word, e.g.:

```python
uses_turbo = any(
    words[:1] == ["turbo"] or words[:2] in (["npx", "turbo"], ["pnpm", "exec"], ["yarn", "exec"])
    for seg in segments
    for words in [seg.split()]
    if words
)
```
(sketch — needs `words[1] == "turbo"` for the exec forms; left as a suggestion, not applied.)
