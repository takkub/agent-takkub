# #164 + #166 — `send` "unknown role" mislabel + orphaned ledger rows

## #164 — `takkub send --to <role>` said "unknown role" for a role that IS registered

### Repro (reported)

`backend` is a real role in `roles.py`, but its pane had been closed. `takkub send --to
backend "x"` returned exit 1 `"unknown role: backend"`, indistinguishable from typing a
role name that never existed.

### Root cause

`Orchestrator.send()` (`orchestrator.py`) looks up the *pane widget* via
`self._project_panes(project).get(to_role)`. That dict is populated by `register_pane()`
and — critically — `unregister_pane()` (`spawn_engine.py:850`) **pops the entry out
entirely** when a pane closes:

```python
pane = self._project_panes(project).pop(role_name, None)
```

So `pane is None` collapses two very different situations into one message:

1. `to_role` was never a real role at all (typo, made-up name).
2. `to_role` **is** a real role (`roles.by_name(to_role)` finds it) — its pane just
   isn't open right now (closed, or the process restarted and it hasn't respawned yet).

`roles.py`'s registry is untouched by pane close/open — only `_panes_by_project` is —
so case 2 is trivially distinguishable from case 1 by checking `roles.by_name()`.

### Fix

Added `Orchestrator._unknown_pane_message(to_role, project_ns)` (`orchestrator.py`),
called from `send()` in place of the flat `f"unknown role: {to_role}"`:

- `roles.by_name(to_role) is None` → unchanged `"unknown role: {to_role}"`.
- Otherwise → `"'{to_role}' is a known role but has no pane open right now — use
  \`takkub assign --role {to_role} "<task>"\` to open one"`.
- If `PaneState.worktree` (`_pane_state[_exit_key(project_ns, to_role)]`) still holds a
  path from a prior `--isolation worktree` assignment — `unregister_pane` never touches
  `_pane_state`, so this survives a pane close — the hint adds: a fresh
  `--isolation worktree` re-assign creates a **new** branch off base, it does not
  continue the old one; to resume that work, assign with `--cwd <old worktree path>`
  instead.

No behavior change for the two pre-existing cases: pane registered but session dead
still returns `"{to_role} is not running (spawn it first)"`; a genuinely unknown name
still returns `"unknown role: {to_role}"`. Shard pane keys (`"qa#1"`) are split via the
already-imported `_split_shard` before the registry check — `roles.by_name` only knows
base names — so a closed shard pane also gets the assign hint instead of a false
"unknown role".

### Tests

`tests/test_send_unknown_role_message.py` (7 cases): unregistered name → unknown role;
registered role, no pane → assign hint, no "unknown role" text; sharded role name
(`qa#1`) resolves against its base role via `_split_shard`, not treated as unknown; pane
present but session dead → unchanged message (regression guard); no pane + prior
worktree → `--cwd` hint with the exact path; no pane + no worktree history → hint omits
`--cwd`; live pane → delivery still works normally.

## #166 — ledger row stuck "working" forever when cockpit closes without `takkub done`

### Repro / confirmed root cause (given, verified by re-reading the code)

- `project_nav.py:410 _pending_task_count()` counts rows with `status == "working"` in
  `.ledger-state.json` to show "N other projects have pending tasks".
- The **only** two call sites that ever flip a row to a terminal status are
  `task_ledger.mark_done()`, invoked from `orchestrator.py:2250` (`done()` → ok/fail) and
  `orchestrator.py:1707` (pane close → `closed`). Both require a live `Orchestrator`
  instance — i.e. a running cockpit process — to fire at all.
- Closing the **project tab** (or the whole cockpit process) is not a call site of
  `mark_done` anywhere. A row left `working` when the process exits has no path back to
  a terminal status; the user cannot clear it themselves.
- `INDEX.md` is a pure regenerated view of `.ledger-state.json` (`_regen_index`) — editing
  it by hand does nothing, the JSON is authoritative.
- There was no reconcile pass anywhere at startup; the only existing "resolve a stale
  open row" path is `create_assignment`'s re-assign-supersede logic
  (`task_ledger.py:235`), which only fires for a role that gets a *fresh* assign — a role
  nobody ever assigns again stays orphaned indefinitely.

### Fix — two parts

**1. Startup reconcile (automatic).** `Orchestrator.__init__` (`orchestrator.py`), in the
same best-effort/non-fatal block group as the existing orphan-worktree/transcript prunes
(all of which run "before any pane is alive" at boot), now calls
`task_ledger.reconcile_orphaned(project, frozenset())` for every project returned by
`task_ledger.list_projects_with_ledger()`.

**2. `task_ledger.reconcile_orphaned(project, live_roles, today=None)`** (new,
`task_ledger.py`) — flips every `"working"` row for a role in `state["open"]` to
`"closed"` with `row["reason"] = "orphaned"` (status vocabulary unchanged, reason is a
new optional field consumed by `_status_suffix` to render `"➖ ปิด (orphaned — session
ไม่มีแล้ว)"`, distinct from an ordinary close). Rows are **flipped, never deleted** —
history stays visible in `INDEX.md`.

**The safety gate — `_orphan_candidates(state, live_roles, today)`** — is the part that
actually matters, and it requires *both*:

1. **`ptr["date"] < today`** (the row's assign date is strictly before today). This is
   the primary guard. `spawn_engine._auto_respawn` can bring a crashed/restarted pane
   back a few seconds after boot using its cached `last_assigned_task` — critically, that
   path **never calls `create_assignment`**, so a respawned pane's row is *supposed* to
   still say `"working"`. Since respawn only ever concerns *today's* work, gating on date
   means the reconcile pass — which runs at `__init__` time, before any pane (including a
   respawning one) exists — can never race a legitimate same-day respawn. A row from
   yesterday or earlier is never going to auto-respawn back to life.
2. **`role not in live_roles`** — belt-and-suspenders for the edge case where a
   stale-dated row's pane is somehow still alive (cockpit left running across midnight).
   At boot time `live_roles` is always empty (no pane exists yet), so guard #1 alone
   already does the real work there; guard #2 matters for the CLI-triggered manual
   `task reconcile` call, run any time *after* boot once panes are live.

Two cockpit instances (dev repo vs. prod `~/.agent-takkub`, confirmed to run
simultaneously on this machine) never collide here: each instance's `RUNTIME_DIR` — and
therefore its `.ledger-state.json` — is already instance-scoped, so a reconcile pass only
ever sees its own process's panes and its own ledger file.

**3. Manual escape hatch — `task_ledger.close_role(project, role, live_roles, force)`** —
explicit, user-directed, so it is **not** date-gated (the user already knows what they're
doing), but it still refuses a role with a currently live pane unless `--force` is
passed, so it can never be used to accidentally paper over real in-progress work.

**4. CLI** (`cli.py`, lead-only via a new `_require_lead_for_task_admin` gate — same
shape as the existing `_require_lead_for_pane_tools`; `task show` stays open to
teammates):

```
takkub task reconcile [--dry-run]
takkub task close --role <r> [--force] [--dry-run]
```

Both route through `cli_server.py`'s new `"task-reconcile"` / `"task-close"` IPC
commands to `Orchestrator.task_reconcile()` / `Orchestrator.task_close_role()`, which
supply the live-pane set (`_live_roles()`: roles with a pane whose `session.is_alive`)
that `task_ledger`'s gate needs — `task_ledger.py` itself has no notion of a live pane.
`--dry-run` previews the exact set of rows that would close (or, for `close`, whether the
live-pane guard would block it) without writing anything.

### Tests

- `tests/test_task_ledger.py` (`TestReconcileOrphaned`, `TestCloseRole`, 9 cases): closes
  a backdated row; **leaves a same-day row untouched even with zero live panes** (the
  core #166 safety property); leaves a backdated row alone when its role has a live pane
  (belt-and-suspenders); no-op with no open rows; `preview_reconcile` reports candidates
  without mutating state; `close_role` closes/refuses-without-force/force-overrides/
  errors-on-no-open-row.
- `tests/test_task_reconcile_orchestrator.py` (8 cases): orchestrator-level
  `task_reconcile`/`task_close_role` wiring — live-pane detection integrated correctly,
  dry-run previews never mutate, a role with a live pane is never closed even when its
  row is backdated.
- `tests/test_task_reconcile_close_cli.py` (8 cases): both subcommands blocked for a
  non-lead caller *before* any request reaches the orchestrator (mocked `_request` never
  called); `task show` stays open; request payloads carry the right `cmd`/`dry_run`/
  `force` fields; failure responses exit non-zero.
