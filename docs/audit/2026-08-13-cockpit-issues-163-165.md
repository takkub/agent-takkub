## #165 — evidence screenshot ของ role อื่นถูกแนบผิด

### Root cause
`Orchestrator._scan_done_evidence` (orchestrator.py) มี 2 ชั้น:
1. สแกน `<artifacts_dir>/<role>/` ของ pane เอง (แม่นยำ, self-attributed)
2. **fallback**: ถ้าไม่เจอ สแกน `<artifacts_dir>` ทั้งก้อนแบบ recursive (`rglob("*")`) — ครอบคลุมทุก
   sub-folder ของ**ทุก role** ในโปรเจกต์เดียวกัน

Fallback ชั้น 2 ถูกออกแบบไว้ตั้งใจ (#109) สำหรับ convention "qa เซฟ screenshot ไว้ที่
`screenshots/` แบบแบน แล้ว critic ไปหยิบมาอ้างอิงเป็น evidence" — แต่โค้ดเดิม**ไม่ scope ว่า role ไหนควร
ได้ fallback นี้** เลยรันให้ทุก role รวมถึง role ที่ไม่เกี่ยวกับ screenshot เลย (backend/devops ที่ทำงาน
python ล้วนๆ) ผลคือ ถ้า role นั้นไม่มี subdir ของตัวเอง (ซึ่งเป็นปกติสำหรับ role ที่ไม่ capture ภาพ) แล้ว
มี role อื่น (เช่น critic) เซฟภาพเข้า project artifacts dir ในช่วงเวลาที่ assign-window ของ backend
ครอบคลุมพอดี → backend ได้ evidence ของ critic ไปแนบใน done() report ของตัวเอง ติดป้าย `(shared dir)`
แต่ Lead อ่านผิวๆ ไม่รู้ว่าเป็นภาพข้าม role

พิสูจน์ตรงกับเคสจริงที่ Lead รายงาน: backend (python ล้วน, ไม่มี subdir ของตัวเอง) ได้ภาพ 3 ใบของ critic
(`new_role_full.png` ฯลฯ) แนบมาพร้อม tag `(shared dir)` — ตรงกับ mechanism ทุกจุด

### Fix
Scope fallback (ชั้น 2) ให้รันเฉพาะ `base_role in _EVIDENCE_WARN_ROLES` (`qa`, `critic`, `designer`,
`reviewer`) — role กลุ่มเดียวที่ qa→critic screenshot-sharing convention ใช้จริง ชั้น 1 (subdir ของตัวเอง)
ยังทำงานเหมือนเดิมสำหรับทุก role (ไม่มีความกำกวมเรื่อง attribution)

```python
found = cls._find_evidence_files(artifacts_dir / base_role, assign_ts, now)
shared = False
if not found and base_role in _EVIDENCE_WARN_ROLES:   # ← เพิ่ม guard
    found = cls._find_evidence_files(artifacts_dir, assign_ts, now)
    shared = True
```

`src/agent_takkub/orchestrator.py` — `_scan_done_evidence`

### Test
`tests/test_done_evidence.py`:
- `test_non_warn_role_never_cross_attributes_shared_dir` — backend + critic's screenshot ใน artifacts
  dir เดียวกัน → backend ได้ `""` (ไม่ใช่ critic's evidence)
- `test_non_warn_role_still_gets_its_own_subdir_evidence` — backend ที่มี subdir ของตัวเองยังได้ evidence
  ปกติ (ชั้น 1 ไม่กระทบ)
- แก้ 2 เทสเดิมที่ **pin พฤติกรรมบั๊กไว้ตรงๆ** (`test_falls_back_to_shared_dir_when_no_role_subdir`,
  `test_fallback_can_still_cross_attribute_when_own_subdir_empty`) ให้ใช้ role `qa`/`critic` (warn-role
  จริง) แทน `backend` — ยัง cover behavior ที่ตั้งใจเก็บไว้ (qa→critic legit) ได้เหมือนเดิม

## #163 — pane หายจาก `takkub list` ก่อน done report ถึง Lead

### Timeline จริง (จาก Lead, แก้ไขรอบสอง)
- 15:10:27 — backend (`agent-takkub` project) เขียน session report + commit `593969c` เสร็จ, เรียก

- ~15:40 — Lead Inbox Digest ของ done ตัวนี้เพิ่งมาถึง (ดีเลย์ ~30 นาที ไม่ใช่หาย)
- ระหว่างนั้น Lead pane ทำงานต่อเนื่อง (busy) ตลอด

**หมายเหตุ:** ไม่สามารถอ่าน `runtime/events.log` จริงของ prod cockpit มายืนยัน timestamp ระดับ event
ได้ (`C:/Users/monch/.agent-takkub/` เป็น dir ต้องห้ามตามนโยบายงานนี้) ข้อสรุป root-cause ด้านล่างมาจาก
source trace + deterministic test เท่านั้น ไม่ใช่จาก log ของ incident นี้โดยตรง — ระบุไว้ให้ชัดเพื่อไม่ให้ blur
กับ "พิสูจน์แล้ว"

### Race ที่พิสูจน์ได้จาก source (deterministic, มี test คุม timer)

`Orchestrator.done()` (orchestrator.py) ทำ 2 อย่างที่ **อายุไม่เท่ากัน** สำหรับ pane เดียวกัน:

1. เรียก `_notify_lead()` → ถ้าเป็น clean done notice (`[<role> done] ...`) ถือว่า *digestible* → เข้า
   `_lead_digest_queue` แล้ว arm timer **`window_ms` (default `_INBOX_DIGEST_WINDOW_MS = 60_000` ms)**
   ก่อนถึงจะ flush เข้า live queue แล้วค่อยเขียนจริงผ่าน `_pump_lead_notify` (ซึ่งมี busy-retry cap ของ
   ตัวเองอีก ~30s ก่อน spill ไปที่ `_pending_done_notices` ถ้า Lead ไม่ ready)
2. Schedule ปิด pane ตัวเอง — **`QTimer.singleShot(2_500, _close_if_same_session)`** คงที่ ไม่ผูกกับ
   สถานะการส่ง notice เลย

`close()` เองไม่ได้ pop pane ออกจาก `_project_panes` ตรงๆ — มันแค่ `paneClosed.emit()` แล้ว
`main_window.py`/`headless_window.py` (ทั้งคู่ wiring เหมือนกัน) เป็นคนเรียก `unregister_pane()` จริงตอน
รับ signal — จบลงที่ pane หายจาก `_project_panes` ภายใน ~2.5s หลัง `done()` เสมอ ไม่ว่า notice จะถูก
ส่งจริงหรือยัง

`list_status()` / `list_status_detailed()` (backing `takkub list`/`takkub status`) อ่านจาก
`_project_panes` ตรงๆ — เมื่อ pane หายไป role ก็หายจาก list ทันที **ไม่ว่า notice จะยังค้างอยู่ใน
digest queue / live queue / durable pending store แค่ไหนก็ตาม**

= pane หายจาก list ที่ ~2.5s ทุกครั้ง แต่ notice อาจใช้เวลาถึง 60s (digest) + ~30s (busy-retry) + เวลา
เท่าไหร่ก็ได้ในกรณี draft-hold (ดูหัวข้อถัดไป) กว่าจะถึง Lead จริง — ช่องว่างนี้คือที่มาของอาการที่ Lead เจอ
(reproduce ได้ deterministic ผ่าน `tests/test_pending_done_notice_visibility.py::TestDoneCloseRacesDigestDelivery`)

### เรื่อง "1800s ceiling" ที่ Lead สงสัยว่าเป็นตัวเดียวกัน — **ไม่ใช่ code path เดียวกัน**

`BUSY_WAIT_CEILING_SEC = 1800` (orchestrator.py) ถูกใช้จุดเดียวคือใน `_send_when_ready()`
(lead_inbox.py:814) — เส้นทาง **Lead → teammate** (ตอน Lead `assign` งานแล้วรอ pane teammate นั้นถึง
ready prompt ก่อน paste task) **คนละทิศทางกับ done-notice (teammate → Lead)** ที่ #163 เจอ

เส้นทาง teammate → Lead (`_notify_lead` → digest → `_pump_lead_notify` → `_pending_done_notices` →
`_reap_pending_done_notices`) มี ceiling ของตัวเองแยกกัน 3 ชั้น ไม่แตะ `BUSY_WAIT_CEILING_SEC` เลย:

| ชั้น | timeout | ถ้าเกิน |
|---|---|---|
| digest window | `_INBOX_DIGEST_WINDOW_MS` = 60_000 ms | flush เข้า live queue |
| live-queue pump busy-retry | `LEAD_NOTIFY_BUSY_CAP` = 75 × 400ms ≈ 30s | spill ไป `_pending_done_notices` (durable) |
| durable reaper, Lead not-ready ต่อเนื่อง | `_DONE_NOTICE_STALE_S` = 60.0s | force-deliver ผ่าน `_force_deliver_done_notices` (bypass ready-gate) |
| durable reaper, Lead ready แต่ **draft-hold** (มี unsubmitted text ค้าง) | **ไม่มี ceiling เลย (ตั้งใจ, #118)** | รอจนกว่า draft จะหายไปเอง |

รวม 3 ชั้นแรก worst-case ≈ 150s ไม่ใช่ 1800s — **ไม่ตรงกับ literal 1800s ceiling ที่ Lead สงสัย** จึง
สรุปว่า**ไม่ใช่บั๊กเดียวกันกับ BUSY_WAIT_CEILING_SEC** อย่าไปแก้ตัวเลขนั้นซ้ำที่นี่

ผู้ต้องสงสัยที่แรงกว่าและพิสูจน์ได้จาก source (ไม่ใช่เดา): **ชั้นที่ 4 (draft-hold) ไม่มี ceiling เลยโดย
ดีไซน์** — comment เดิมใน `_reap_pending_done_notices` บอกตรงๆ ว่า "Park indefinitely… never
force-bypassed" (อ้างอิง #118: force-flush ทับ draft ที่กำลังพิมพ์อยู่ แย่กว่า notice มาช้า) ถ้า Lead
เข้า-ออก branch นี้ระหว่าง 30 นาที (เช่น composer อ่านเป็น "ready" ชั่วครู่ระหว่าง tool-call แต่ไม่ว่างจริง)
การรอจะไม่มีสัญญาณอะไรเลยจนกว่าจะหลุดออกจาก branch นี้ได้เอง — ตรงกับอาการ "เงียบ 30 นาทีแบบไม่มี
ร่องรอย" ที่ Lead เจอ **แต่ยืนยันแน่ชัดว่าใช่ path นี้จริงในเคสวันนี้ไม่ได้เพราะอ่าน log จริงไม่ได้** — ระบุเป็น
สมมติฐานที่แรงที่สุดจาก source เท่านั้น

### Fix ที่ทำจริง (เจตนา จำกัด scope, ไม่แตะ delivery-timing logic)

**พิจารณาแล้วไม่ทำ:** ใส่ ceiling ให้ draft-hold branch แล้ว force-deliver ผ่าน
`_force_deliver_done_notices` เหมือนชั้น 3 — ตรวจโค้ดแล้วพบว่า `_force_deliver_done_notices` เขียนทับ
composer ตรงๆ โดยไม่สนใจ draft ที่มีอยู่ (`sess.write(payload)` blind) — ถ้าเอามาใช้กับ draft-hold branch
จะ**รีโปรดิวส์บั๊กเดิมที่ #118 แก้ไปแล้ว** (clobber draft จริงของผู้ใช้) แค่ดีเลย์ไปอีก 30 นาที ไม่ใช่ทางแก้ที่ปลอดภัย
— ตัดสินใจไม่ทำ ใส่ comment อธิบาย tradeoff นี้ไว้ที่ `_reap_pending_done_notices` แทน (ไม่มีการเปลี่ยน
behavior จุดนี้)

**ทำจริง:** แก้ที่จุดสังเกตการณ์ (`takkub list`/`takkub status`) แทนจุดส่ง — ปลอดภัยกว่าเพราะเป็น
read-only channel ไม่ต้อง inject เข้า composer ของ Lead เลย แก้ได้ตรงกับ req #4 ที่ Lead ขอ
("อย่างน้อยที่สุด ต้องมีร่องรอยให้เห็นว่ามี notice ค้างอยู่ในคิว") โดยไม่เพิ่มความเสี่ยงใดๆ ต่อ delivery
pipeline ที่ hardened มาหลายรอบแล้ว (#22/#26/#70/#108/#118/#130/#133/#144)

`orchestrator.py`:
- `Orchestrator._has_pending_lead_notice(project_ns, role_name)` — สแกน `_lead_digest_queue`,
  `_lead_notify_queue`, `_pending_done_notices` หา notice ของ role นั้น (match ทั้ง raw tag
  `[role done]`/`[role FAILED]` และ digest-formatted `• [role] done`)
- `Orchestrator._pending_notice_roles(project_ns, known)` — จาก `_recent_done` (20 รายการล่าสุด, มีอยู่
  แล้ว) หา role ที่ไม่มี live pane แล้ว แต่ notice ยังค้าง

  `Orchestrator._PENDING_NOTICE_STATE` ("done (report queued — not yet delivered to Lead)") จนกว่า
  notice จะถูกส่งจริง (หายจาก queue ทุกที่) ถึงจะหายจาก list ตามปกติ

ผลคือ: role ที่ pane ปิดไปแล้วแต่ notice ยังไม่ถึง Lead จะ**ไม่หายเงียบๆ**จาก `takkub list`/`status`
