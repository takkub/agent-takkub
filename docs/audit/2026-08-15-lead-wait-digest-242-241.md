# Lead wait primitive (#242) + digest staleness/truncation (#241)

2026-08-15 · backend

## Source

Both issues were filed by the Lead of this project's own cockpit session, same day: Lead hand-rolled
a background polling loop around `takkub status` waiting for teammates to finish, forgot to stop the
old one before starting a new one, and six such loops accumulated concurrently — each hitting the
cockpit socket every 40s for nothing, on a machine with the prod cockpit doing real work. The user's
explicit instruction: fix this at the **middle layer** (the cockpit itself, provider/project-neutral),
not just patch this one Lead session.

## #242 — `takkub wait`

### Root cause

There was no cockpit primitive for "block until a teammate's report has actually reached Lead." Every
Lead across every project had to invent the same shape of loop, and the two obvious building blocks
both had known problems documented in prior issues:

- `takkub status` (`Orchestrator.pane_status_report`) is a point-in-time snapshot, not a wait — polling
  it requires the caller to write the loop, decide the poll interval, and decide when to stop. Nothing
  stopped a stale loop from a previous Lead turn continuing to run once a new one started.
- A role vanishing from `takkub list` was never a reliable "done" signal on its own (#163, #225,
  #236 — a pane can disappear from the registry before its report is actually delivered into Lead's
  pane; already fixed, but the fix was "surface a pending state," not "give Lead something to block on").

### Fix

New `LeadWaitMixin` (`src/agent_takkub/lead_wait.py`, mixed into `Orchestrator` the same way
`LeadInboxMixin`/`AutoResumeMixin` are) plus `takkub wait [--role <r>]... [--timeout <s>]`:

- **`begin_wait(project_ns, roles, timeout_s)`** registers a wait. Empty `roles` defaults to every
  role `list_status` currently tracks for the project (Lead excluded). At most **one** `_active_waits`
  registration per project — a second `begin_wait` call while one is outstanding **attaches** to it
  (unions the role set, keeps the earlier `started_ts`, takes the larger timeout) instead of creating
  an independent poll loop. This is the direct fix for the "6 loops stacked" failure mode: it is no
  longer possible to have two live registrations for the same project at once. A registration whose
  owner never called `end_wait` (crash, Ctrl-C, killed pane) and has gone silent past its own timeout +
  a 120s grace window is treated as abandoned and replaced — no periodic QTimer reaper needed.
- **`poll_wait(project_ns, wait_id)`** is one cheap poll tick: for each registered role it checks
  `_wait_done_events[(project_ns, role)]` (a new, minimal record `done()` writes — see below) and, if a
  resolution happened *after* the wait started, cross-checks `_has_pending_lead_notice()` (the exact
  #231 signal `takkub inbox` already trusts) to confirm the report has actually left the
  digest/live/durable pipeline, not just that `done()` was called. A role resolves to `"done"` or
  `"failed"` only once **both** are true. Still-pending roles get a specific reason: working, stalled N
  minutes, stuck at a tty prompt (`PtySession.is_blocked_on_tty_prompt()`), report generated but not
  yet delivered, or role never spawned. `panes`/`list_status_detailed` are computed **once per poll
  tick**, not once per role, so one tick is O(roles), not O(roles²).
- **`end_wait(project_ns, wait_id)`** explicit early release (Ctrl-C). Not needed on the success path —
  `poll_wait` auto-removes the registration once every role resolves or the timeout fires.
- A "completion before the wait started" is deliberately ignored — same staleness philosophy as #241's
  dedup rule below: `wait` reacts to *new* completions from the moment it started watching, not
  whatever already happened.

**Where the blocking loop actually lives:** `CliServer` runs every request on the Qt main thread
(`cli_server.py`'s own module docstring), so nothing server-side may block it — `poll_wait` had to stay
a single cheap read. The loop itself is `cli.cmd_wait`, a single `takkub wait` process's own bounded
sleep loop (polling `wait-poll` with a 4s→15s backoff), replacing every Lead-authored equivalent by
construction rather than by policy alone. `--timeout` is always required to have a value: no explicit
flag uses a 1800s default, and any value is clamped into `[5s, 7200s]` — never an unbounded block.

Multi-provider: the poll loop only reads pane/queue state the orchestrator already tracks per role
(`_wait_done_events`, `_has_pending_lead_notice`, `list_status_detailed`) — nothing here is
Claude-specific, so it works identically regardless of which CLI backs a given role's pane.

Wiring: `cli.py` (`cmd_wait`, `"wait"` added to `LEAD_ONLY_COMMANDS`), `cli_server.py` (`wait-begin` /
`wait-poll` / `wait-end` dispatch, all three added to `_LEAD_ONLY_CMDS` — same read-sensitivity
rationale as `inbox`), new import-linter contract `lead-wait-layer` (mirrors `lead-inbox-layer`:
`lead_wait.py` must not import `orchestrator`/`main_window`/`app`/`cli`).

### `done()` touch — minimal by design

`backend#3` was concurrently editing `orchestrator.py` in another worktree. `done()` itself only
gained two additive lines right next to the existing `_recent_done.insert(...)` call — recording
`_wait_done_events[(project_ns, from_role)] = {"ts": ..., "failed": ...}` via `getattr(self,
"_wait_done_events", {})` (never raises on a partial test fixture that bypasses `__init__`). No
existing line in `done()` was modified.

## #241 — digest staleness, truncation, dedup

Reported symptom: three done reports in a row (`saas_admin`, timestamps in the filenames) where the
Lead Inbox Digest arrived *after* Lead had already read the report through a hand-rolled
`runtime/sessions/**` file-watcher workaround — itself a symptom of not having #242 yet. Sub-issues,
addressed in order of the issue's own cost/value ranking:

### B — timestamp + age in the digest (implemented)

`_lead_digest_queue` entries gained a third tuple element, `queued_ts` (`time.time()` at enqueue) —
`(body, pane_token, queued_ts)`. `_format_digest_item` now prefixes each rendered line with
`[HH:MM:SS · Ns/Nm ago]` when a timestamp is known. `_unwrap_notice_item` was generalized to always
return `(body, pane_token, queued_ts)`, with `queued_ts` reading back `None` for the live queue's
2-tuples (delivered promptly enough that staleness isn't a concern there) and for legacy bare-string
entries. `takkub inbox`'s digest-tier items also gained a `queued_ts` field, and `cli.py`'s
`_print_inbox_items` renders the same "queued Xs/Xm ago" suffix — so both surfaces (the pushed digest
and the pulled `inbox` read) show freshness the same way.

### A — dedup against content Lead already pulled via `takkub inbox` (implemented)

`Orchestrator.inbox_report()` (the `takkub inbox` backing call) now fingerprints every body it returns
(`_notice_fingerprint` — sha1 of the stripped body, truncated to 16 hex chars) into a new
`_inbox_seen[project_ns]` set. When `_flush_lead_digest` later renders that same item out of the
digest queue, a fingerprint match collapses the line to `• [role] (อ่านแล้วผ่าน takkub inbox · age)`
instead of re-pasting content Lead has already read.

Scope note, not hidden: this only catches the *provable* case — Lead explicitly pulling content via
`takkub inbox` (or, going forward, `takkub wait`'s underlying signal). It does not and structurally
cannot detect "Lead read the raw session-md file directly with the Read tool," since the orchestrator
has no visibility into that. The real fix for *that* channel is #242 removing the incentive to build a
file-polling workaround in the first place — the root cause the issue itself named. Inventing a
speculative "mark seen" heuristic for content the orchestrator can't observe was avoided rather than
guessed at.

### C — mid-sentence truncation (partially pre-existing, word-boundary bug fixed)

Investigation (not guessed — traced every char-slice in the notify path): the live digest path does
**not** truncate short/medium notes at all — anything under `TASK_HANDOFF_THRESHOLD` (400 chars)
passes through `_format_digest_item` unmodified. The one real truncation site in the notify path is
`_condense_done_note`'s headline for notes ≥400 chars: first line, hard-cut at 200 chars + "…". That
already followed the issue's own suggested design (a short line + a `📄 รายงานเต็ม: <path>` pointer to
the full text) — nothing is actually lost. The bug was that the 200-char cut was a **hard character
slice**, which could sever a word or identifier mid-way when a long single-line note happened to have
its nearest space past the 200-char mark. Fixed with a shared, tested helper,
`_truncate_at_word_boundary(text, max_chars)` (`orchestrator_text.py`): backs up to the nearest
preceding space unless that space is too early to be a real word boundary (`< max_chars * 0.6`, in
which case a single unbroken token exceeds the budget and the old hard-cut behavior is kept, verified
by `test_orchestrator_text_notice_helpers.py`'s `test_single_long_token_falls_back_to_hard_cut` case).

### D — `takkub inbox [--unread]` to pull instead of waiting on push

Already shipped in #231 (`takkub inbox [--role <role>]`, this same 2026-08-15 session, prior commit).
No further work needed here.

## Central-doc fix (issue's requirement 3 — provider/project-neutral)

Traced the actual cross-project injection path rather than guessing which doc "feels" central:
`Orchestrator`/non-Claude spawn → `lead_context._build_lead_context_text()` → `cockpit_md =
ASSETS_ROOT / "CLAUDE.md"`. In a dev checkout, `ASSETS_ROOT == REPO_ROOT`, so this is literally this
repo's own root `CLAUDE.md` — the exact file this session's Lead was spawned with. This text is written
to `runtime/lead-context.md` (`--append-system-prompt-file`, Claude Lead) **and** to
`<project_cwd>/AGENTS.md` (`render_lead_agents_md`, every non-Claude Lead provider) for **every**
project, every session, every provider — confirmed by reading both call sites and their docstrings,
not assumed from the filename. This is the one true central source; project-specific generated
CLAUDE.md files (`project_rules.py`) are a different, per-project concern (tech stack/business rules)
and are not where operational cockpit behavior belongs.

Added to this repo's root `CLAUDE.md` under "กฎที่เคยพลาด" (baked into every future Lead spawn's system
prompt, every project, every provider):

- **ห้ามกอง background waiter** — use `takkub wait` instead of a hand-rolled loop; at most one waiter
  per project (new `wait` auto-attaches); named the specific self-defeating-exit-condition anti-pattern
  ("ออกเมื่อไม่มีใคร working" invalidated by Lead's own next dispatch) as a hard-banned shape, with the
  2026-08-15 incident as the concrete example.
- Quick-reference block gained `takkub wait` / `takkub inbox` one-liners.
- `docs/lead/patterns.md`'s existing parallel-dispatch example used bash's own `wait` builtin (waits for
  `takkub assign`'s immediate "queued" ack, not for the teammate's actual completion) — added a
  clarifying note distinguishing it from `takkub wait` so the two don't get conflated by name alone.
- `docs/lead/cli-reference.md` gained the full `takkub wait` entry alongside the existing `inbox` one.
