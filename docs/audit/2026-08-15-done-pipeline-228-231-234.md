# Done pipeline: #228 phantom reports, #231 unreadable inbox, #234 progress kills subprocess

2026-08-15 · backend

## #228 — phantom done report

### Root cause (proven, not guessed)

Every Lead-facing done/FAILED notice passes through `Orchestrator._notify_lead()`
(`lead_inbox.py`), which routes it into one of three queues depending on
Lead's state at the moment:

1. `_lead_digest_queue` — debounced up to `TAKKUB_INBOX_DIGEST_MS` (default
   60s) before being folded into one combined "Lead Inbox Digest" message.
2. `_lead_notify_queue` — the ready-prompt-aware live delivery queue (busy
   retries up to `LEAD_NOTIFY_BUSY_CAP` ≈ 30s before spilling further).
3. `_pending_done_notices` — the durable store (survives a restart,
   delivered on Lead's next spawn or by `_reap_pending_done_notices`, no
   time ceiling when a genuine unsubmitted draft is blocking delivery).

Before this fix, every one of these queues stored **only the already-
rendered notice text** — a plain string such as `[frontend#1 done] …` — with
**no binding to which pane process instance actually produced it**. The
`from_role` string in that text is just a label; nothing checked whether the
pane currently running under that role name (`_project_panes[role]`) was
still the same process that generated the note by the time the queue item
was finally delivered.

Confirmed independently, not inferred:

- `spawn_engine._mint_pane_token()` mints a brand-new random token per spawn
  and immediately **revokes the previous token for the same
  `(project_ns, role_name)` pair** — so a respawned role slot genuinely gets
  a new identity server-side; the old pane's token stops authenticating.
- Nothing that touches `_lead_digest_queue` / `_lead_notify_queue` /
  `_pending_done_notices` ever checked that identity. `orchestrator.py`'s
  `_has_pending_lead_notice()` / `_pending_notice_roles()` (added for #163)
  match a queued notice to a role by **string only** — `item.get("role") ==
  role_name` — with no session/spawn-instance component at all.
- `spawn_engine.py` has no code path that purges or re-tags a role's queued
  notices when that role is respawned mid-session; the only queue-flush
  trigger tied to spawning is Lead's own spawn flushing `_pending_done_notices`.

So the mechanism the issue's own investigation note suspected is real and
provable: pane A (role `frontend#1`) calls `done()` with a genuine, detailed
note. Delivery is delayed for any of the three reasons above. Before it
flushes, `frontend#1` is respawned — pane B now owns that role name. The
queued notice, still just a bare string tagged `[frontend#1 done]`, is
delivered later and reads identically to a report from the pane currently
running under that name. Lead has zero signal the underlying process
changed. Pane B, asked about it afterward, correctly says it never called
`done` — because it didn't; pane A did, before it was replaced.

What this audit did **not** find, and is not claiming: no code path
synthesizes a done report from a transcript scan, a stale on-disk file, or
any other source. Every phantom notice traces to a genuine `done()` call —
just from a pane instance that no longer exists by delivery time.

### Fix

Bind every queued notice to the calling pane's own auth token, captured at
the moment `done()` runs (before any teardown — `close()` only revokes the
token 2.5s later):

- `spawn_engine._current_pane_identity(project_ns, role)` — new helper,
  returns the token currently minted for a role slot (or `None`).
- `Orchestrator.done()` captures `origin_pane_token =
  self._current_pane_identity(project_ns, from_role)` up front and threads
  it into `_notify_lead(..., pane_token=origin_pane_token)`.
- `_notify_lead` carries `pane_token` into every queue: `_lead_digest_queue`
  and `_lead_notify_queue` entries are now `(body, pane_token)` tuples
  (`_pending_done_notices` entries — already dicts — gained a
  `"pane_token"` key). Every existing spill path (Lead-died, busy-cap,
  draft-hold-expired, write-failure, `_flush_pending_done_notices`) carries
  the token forward instead of dropping it.
- At the point a notice is actually about to reach Lead —
  `_flush_lead_digest` (per digest item) and `_pump_lead_notify` (the live
  queue's delivery write), plus `_force_deliver_done_notices` (the staleness
  reaper's last-resort bypass) — `_provenance_stale(project_ns, role,
  pane_token)` re-checks `_current_pane_identity()` against the recorded
  token. A mismatch (respawned) or `None` (role no longer has any live pane)
  prefixes the delivered text with an explicit banner:
  `⚠️ [unverified origin — <role> pane was respawned since this report was
  queued; confirm current status with the live pane before acting on it]`.
- A body with no role-attribution (`_notice_role_tag()` returns `None` —
  system notices, CC relays, the combined digest header) or no recorded
  token (legacy/system-authored) is never flagged — there is nothing to
  verify, so it is left alone by design, not silently trusted as "confirmed".

This is "flag, don't silently withhold" per the task's own two acceptable
options — a stale report still reaches Lead (so nothing is lost), but it
can no longer be mistaken for a fresh, trustworthy report about the pane
currently running.

Known residual gap (documented, not hidden): a queued item that never
enters any of the three queues checked here — i.e. is a plain string
constructed directly by a test fixture or a future caller that bypasses
`_notify_lead` — carries no origin and is treated as trusted. All real
production paths go through `_notify_lead`, so this only matters for code
that doesn't yet exist.

## #231 — Lead had no way to read a queued report's content

### Root cause

`takkub status` (`Orchestrator.pane_status_report` /
`_pending_notice_roles`) could only ever report the fixed string
`"done (report queued — not yet delivered to Lead)"` — a boolean-ish state
tag, never the note text itself. No CLI subcommand read
`_lead_digest_queue` / `_lead_notify_queue` / `_pending_done_notices`
back out; `takkub done --role X` doesn't exist (`done` is `[note] --fail`
only, teammate-side). The only path left was Lead Glob-searching
`runtime/sessions/**` by hand, which times out (4780+ files) without a
narrow path guess.

### Fix

New Lead-only, read-only command: `takkub inbox [--role <role>]`.

- `Orchestrator.inbox_report(project, role=None) -> list[dict]` (in
  `orchestrator.py`, next to `_pending_notice_roles`) reads all three queue
  tiers and returns `{role, queue, body, origin_confirmed}` per item —
  reusing the exact #228 provenance check so a stale item is flagged here
  too, before Lead ever acts on it, not just at eventual delivery time.
- `cli_server.py`: `cmd == "inbox"` dispatch, gated via the same
  `_LEAD_ONLY_CMDS` + Lead-token mechanism `status`'s sensitive fields
  already use (M3#16 precedent) — a confused teammate shell cannot read
  other panes' report bodies.
- `cli.py`: `cmd_inbox` / `takkub inbox` subcommand, `"inbox"` added to both
  `LEAD_ONLY_COMMANDS` (CLI-level role gate, defense-in-depth alongside the
  server-side gate — same two-layer pattern `assign`/`spawn`/`close` use)
  and the printer (`_print_inbox_items`) that renders each item with a
  `⚠ unconfirmed origin` marker when `origin_confirmed is False`.
- `docs/lead/cli-reference.md` updated with the new command.

Not done (deliberately out of scope for this pass): rewriting
`pane_status_report`'s `done_events` to print absolute paths instead of
basenames, per the issue's secondary suggestion — `takkub inbox` solves the
actual blocking problem (reading the content) more directly than fixing the
path string would have, and doing both would have widened the diff for a
cosmetic win. Flagged here rather than silently dropped.

## #234 — `takkub done` mid-task kills the pane's subprocess tree

### Root cause

`Orchestrator.done()` unconditionally schedules `_close_if_same_session` 2.5s
later regardless of what the note says — there was no "this is a status
update, not completion" signal available. `close()` calls
`pane.session.terminate()`, which kills the whole process tree
(`taskkill /T` on Windows / job-object teardown — `pty_session.py`'s
`terminate()`/`_teardown_resources`). `done` was the pane's *only* channel
back to Lead other than peer `send`, so a teammate mid long-running
subprocess (docker build, migration, e2e suite) with nothing but a status
update to report had no non-destructive option.

### Fix

1. **`takkub progress "<msg>"`** — new command, same one-line "tell Lead
   what's happening" primitive as `done()`'s notice, with every teardown
   side effect removed: no auto-close timer, no `_pane_state`/`_idle_state`
   pop, no resource-slot release, no worktree merge-proposal, no
   task-ledger flip. `Orchestrator.progress()` (orchestrator.py, right after
   `done()`) tags the message `[<role> progress] <note>` and routes it
   through the same `_notify_lead` pipeline (so it inherits #228's
   provenance machinery for free, though a progress message is never itself
   role-tagged as `done`/`FAILED` so `_notice_role_tag` never matches it —
   nothing to flag). Wired through `cli_server.py` (`cmd == "progress"`,
   same per-pane-token identity gate as `done`/`send` — `from_role` is
   server-derived, not caller-supplied) and `cli.py` (`TEAMMATE_ONLY_COMMANDS`,
   matching `done`'s Lead-cannot-call-this-on-itself gate).
2. **`Orchestrator._warn_if_live_children()`** — best-effort, cross-platform
   (`psutil.Process(pid).children(recursive=True)`, the same idiom
   `app.py`'s stale-process sweep already uses) check called from `close()`
   immediately before `terminate()`. If the pane's shell still has live
   child processes, Lead gets an explicit warning naming the process count
   (and up to 5 process names) *before* they're killed, plus a
   `close_kills_live_children` log event. Never blocks or delays the close —
   psutil failures (no pid, process already gone, permission denied) are
   swallowed silently, matching "at least warn/log" from the issue's own
   proposal rather than the heavier "wait/confirm" option, which would risk
   a hung close on a wedged pane.
3. All 16 `.claude/agents/*.md` role files updated: the 11 full role files
   gained a note under "การรายงานกลับเมื่อเสร็จ" pointing to `takkub progress`
   for mid-task updates; the 5 provider-substitute files
   (codex/gemini/opencode/kimi/cursor) gained the same note under their
   shorter reporting bullet.

Not done: automatically detecting "this note sounds unfinished" from
`done()`'s note text (the issue's third bullet, "ถ้า done note มีสัญญาณว่า
ยังไม่เสร็จ ควรเตือน") — free-text sentiment/completion detection is a much
larger, fuzzier surface than the two structural fixes above and was left
out to avoid a heuristic that's easy to get wrong in both directions
(false positives nagging every legitimate short done, false negatives on
phrasing it doesn't recognize). `takkub progress` removes the actual need
for a teammate to call `done` mid-task in the first place, which is the
more reliable fix for the same problem.
