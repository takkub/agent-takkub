### H2 — shell wrapper, quoted path และ worktree target หลุด destructive-Git guard (#609)

และ `_CMD_START` ที่ `:408`

คำสั่งที่รันได้จริงแต่ classifier อนุญาต:

| รูปแบบ | ช่องโหว่ |
|---|---|
| `git -C "C:/shared project" restore .` | `_GIT_SUBCMD_GAP` ใช้ `\S+` จึงไม่อ่าน quoted path ที่มีช่องว่าง |

| `pwsh -c "git restore ."` | ไม่ unwrap shell |
| `git.exe restore .` | regex ไม่รับ executable suffix |
| `git -c alias.discard=restore discard .` | ไม่ resolve alias / global config argument |
| cwd เป็น worktree แต่ `git -C C:/shared restore .` | `_in_worktree` OR cwd กับ target จึงไม่ยกเลิกสิทธิ์เมื่อ target ออกนอก worktree |

ยิ่งกว่านั้น cwd `.../worktrees/proj/backend-123` ของ frontend ก็ผ่าน:
ไม่มีการตรวจ role/assignment ownership และไม่มีการยืนยันว่า path เป็น worktree จริง

**พิสูจน์จริง:** ใน Git repo ทดลอง stage baseline ของ `work.txt` แล้วเขียนงานใหม่ลง
working file; รูปแบบทั้งหกใน `ART/real_probes.py` ได้ guard allow, Git exit 0 และ
เนื้อหางานใหม่ถูกทับกลับ baseline จริง การทดสอบ pure classifier แยกอีกชุดยืนยัน
`-C` แบบไม่มีช่องว่างจาก worktree ไป shared tree จึงไม่ใช่เพียงผลของ quoted-path bug

**แนวแก้:** parse argv/quoted argument และ shell wrapper ที่รองรับให้ได้ก่อนตรวจ
ตรวจ effective target ของ Git แต่ละ invocation กับ worktree ที่ assignment เป็นเจ้าของ
ส่วน alias ที่ resolve ไม่ได้ต้องไม่ถือเป็น read-only โดยปริยาย
helper บางตัวมีมาก่อน batch; finding นี้คือช่องที่กฎ #609 ใหม่ยังไม่คุ้มครอง

### ยังไม่ปิด — H1/H2 ยังเปิดอยู่ (HIGH ใหม่: bypass คนละรูปแบบ อิมแพคเดียวกับรอบ 1)

รอบนี้ทดสอบ 9 รูปแบบ bypass เพิ่มเติมตามที่ระบุ (wrapper ซ้อน, `--git-dir`/`--work-tree`,
`git -C` แบบ parent, `git worktree remove`/`prune`, `git switch --discard-changes`, env-prefix
`GIT_DIR=x`, pwsh call-operator, `git restore --staged`, `git -c alias.a="!..."`) — 5 รูปแบบถูก
guard บล็อกถูกต้อง (`git -C` parent, call-operator, `restore --staged`, `restore .` เปล่า,
`alias.a="!..."` แบบ shell-out) แต่ **4 รูปแบบยังเปิดจริงและพิสูจน์ด้วยการรันจริง**:

1. **`git --git-dir=<path> --work-tree=<path> restore .`** — `pane_guard.classify` คืน
   `allowed=True`; รันจริงบน fixture ที่มี uncommitted content ทับกลับ baseline สำเร็จ
   (`uncommitted_lost: true`) — อิมแพคเดียวกับ H2 เดิมทุกประการ แค่ใช้ flag คนละคู่กับที่ regex
   คุ้มครอง (`_GIT_SUBCMD_GAP` ไม่รู้จัก `--git-dir=`/`--work-tree=`)
2. **`GIT_DIR=<path> git stash drop`** (env-var prefix ก่อนคำสั่ง) — `classify` คืน `allowed=True`;
   ยืนยันด้วยการรันจริงผ่าน git-bash (shell เดียวกับที่ Bash tool ของ Claude Code ใช้บน Windows
   จริงๆ) กับ stash ของ repo อื่นที่ไม่เกี่ยวกับ worktree เลย — `stash@{0}` หายจริงหลังรัน
   (`before`/`after` ต่างกันจริงใน `ART2/deepdive-results.json`) รุนแรงกว่า H1 เดิมเพราะไม่ต้องพึ่ง
   linked-worktree เลย ชี้เป้า `.git` directory ไหนก็ได้ตรงๆ
3. **`git switch --discard-changes <branch>`** — `classify` คืน `allowed=True`; รันจริงบน
   fixture ที่มี branch `main` จริง ได้ `rc=0` และ uncommitted work หายจริง
   (`uncommitted_lost: true`) พฤติกรรมทำลายข้อมูลเทียบเท่า `checkout .`/`restore .` ที่มี pattern
   คุ้มครองอยู่แล้ว แต่ `switch --discard-changes` ไม่ถูกจับ
4. **`git worktree remove --force <target>`** (และ `prune`) — `classify` คืน `allowed=True` โดย
   ไม่เช็ค ownership ของ **target** เลย (เช็คแค่ cwd ของผู้เรียก) พิสูจน์ด้วยการรันจริง: pane
   frontend (อยู่ worktree ของตัวเอง) สั่ง `git -C <repo> worktree remove --force <backend worktree>`
   ได้จริง ไฟล์ `SECRET UNCOMMITTED WORK` ที่ยังไม่ commit ใน worktree ของ backend หายไปทั้งไดเรกทอรี
   — เป็นช่องทำลายงานของ role อื่นโดยตรง คนละกลไกกับ stash แต่ผลลัพธ์เดียวกัน (data loss ข้าม role)

**หมายเหตุ (ไม่ใช่ finding ยืนยันแล้ว):** wrapper ซ้อนสองชั้น
(`cmd /c "pwsh -c \"git restore work.txt\""`) ก็ได้ `guard_allowed=True` เช่นกัน (
`_unwrap_shell_wrappers` เหลือ escaped quote ค้างและไม่รู้จักว่าเป็นคำสั่ง git) แต่การรันจริงด้วย
quoting แบบนี้กลับเป็น no-op (pwsh ตีความ string ที่หลุด quote มาเป็น literal ไม่ใช่คำสั่งที่ execute)
จึงไม่ทำให้ข้อมูลหายในรูปแบบที่ทดลอง — เป็นช่องโหว่ระดับ classifier logic จริง แต่ยังไม่มี syntax ที่
ทดลองแล้วใช้งานได้จริง ลด severity เป็น LOW/ต้องตรวจเพิ่ม ไม่รวมในคะแนน HIGH ด้านบน

อย่างเดียว — ต้อง parse `--git-dir=`/`--work-tree=`/`GIT_WORK_TREE`/`GIT_DIR` (ทั้ง flag และ env
var) เป็นส่วนหนึ่งของ effective target เสมอ, เพิ่ม `switch --discard-changes` (และ `switch -f`)
เข้ากลุ่ม pattern เดียวกับ `checkout`/`restore`, และให้ `worktree remove`/`prune` ตรวจว่า path
เป้าหมายเป็นของ role/assignment เดียวกับผู้เรียกก่อนอนุญาต ไม่ใช่เช็คแค่ cwd ปัจจุบัน

**3 รูปแบบใหม่ที่ยังเจาะได้จริง (HIGH)** ที่ไม่ใช่ H1/H2 เดิมแต่เข้าข่าย threat model เดียวกัน
(agent ทำลายของ pane อื่นบน shared tree ได้โดยไม่ต้องผ่าน Lead) และ 1 medium + 1 low (defense-in-depth):

**R3-H1 (ใหม่) — symlink/junction ในของ worktree ตัวเอง ชี้ไป shared tree ได้ carve-out ฟรี**

`_worktree_role_owns()` เช็คเฉพาะ**ข้อความ path** ว่ามี segment `<role>-...` อยู่ใต้ `/worktrees/`
หรือไม่ — ไม่เคย resolve symlink/junction เลย พิสูจน์จริงบน Windows ด้วย `mklink /J` (junction,
**ไม่ต้องใช้สิทธิ์ admin** — `os.symlink` ต้องใช้ privilege แต่ junction ไม่ต้อง) สร้าง junction
ชื่อ `link-to-shared` ไว้**ข้างใน** `worktrees/proj/frontend-b3/` (ของตัวเอง) ชี้ไปที่ shared repo
แล้วรัน `git -C <own-worktree>/link-to-shared reset --hard`:

- ข้อความ path `.../worktrees/proj/frontend-b3/link-to-shared` มี segment `frontend-` ตรงเงื่อนไข
  → `classify()` คืน **`allowed=true`** (ได้ carve-out ของ `reset-hard`)
- รันจริง: `git reset --hard` ผ่าน junction สำเร็จ (`rc=0`) และ **`uncommitted_lost=true` จริง** —
  ไฟล์ที่มี uncommitted content ใน shared repo ถูกรีเซ็ตกลับ `baseline` ทันที

รุนแรงกว่า H1/H2 เดิมตรงที่ไม่ต้องพึ่ง `-C`/`--git-dir`/env override เลย — แค่สร้าง junction
ครั้งเดียวไว้ในโฟลเดอร์ตัวเอง (คำสั่งสร้าง junction เองก็ไม่ถูก gate เพราะไม่ใช่ git command) แล้วใช้
`git -C` ปกติทุกครั้งหลังจากนั้นก็เจาะได้เรื่อยๆ

หลักฐาน: `ART3/round3-results.json` case `B3-symlink-junction-into-shared`
(`symlink_setup` แสดง `os.symlink` ล้มเพราะ privilege แต่ `mklink /J` สำเร็จ `rc=0`)

**R3-H2 (ใหม่) — `git apply`/`git apply -R` ไม่ถูก gate เลย ทั้งที่ทำลาย uncommitted work ได้เท่า restore/checkout**

ไม่มี pattern ไหนใน `_GIT_LEAD_ONLY_PATTERNS` ที่รู้จัก subcommand `apply` เลย พิสูจน์จริง: มี
uncommitted content ใน `work.txt`, ทำ `git diff` (read-only, ผ่าน guard ปกติ) ได้ patch ของ diff
นั้นมาเก็บเป็นไฟล์ แล้ว `git apply -R <patch>` reverse-apply กลับ:

- `classify()` คืน **`allowed=true`** (ไม่มี pattern ใดจับ `apply` เลย)
- รันจริง: `rc=0`, **`uncommitted_wiped=true`** — เนื้อหา uncommitted ถูกลบทิ้งกลับเป็น `baseline`
  จริง โดยไม่ผ่านเงื่อนไข worktree/`-C`/env ใดๆ เลย ใช้ได้จาก**ที่ไหนก็ได้**บน shared tree ตรงๆ

นี่คือช่องที่กว้างที่สุดในรอบนี้: agent สามารถ `git diff` (read-only) เพื่อรู้ diff ปัจจุบันของไฟล์ใดๆ
แล้ว craft/`apply -R` ย้อนกลับ (หรือ `apply` ปกติกับ patch ที่ craft เอง) เพื่อ overwrite เนื้อหาไฟล์
ใดๆ บน shared tree แบบเงียบๆ — เทียบเท่า blast radius ของ `restore`/`checkout` แต่ **ไม่ผ่าน pattern
ใดใน `_GIT_LEAD_ONLY_PATTERNS` เลยแม้แต่ข้อเดียว**

หลักฐาน: `ART3/round3-results.json` case `B12-apply-reverse-patch`

**R3-H3 (ใหม่) — `git read-tree --reset -u` ไม่ถูก gate เลย เท่ากับ checkout/restore**

`read-tree --reset -u <tree>` sync ไฟล์ใน working tree จาก tree object ที่ระบุ — blast radius เท่า
`checkout`/`restore` แต่ subcommand คือ `read-tree` ซึ่งไม่อยู่ใน pattern list ใดเลย พิสูจน์จริง:
`classify()` → **`allowed=true`**, รันจริง `rc=0`, **`uncommitted_lost=true`** (ไฟล์ uncommitted
กลับเป็น `baseline`)

หลักฐาน: `ART3/round3-results.json` case `B13-read-tree-reset-u`

**R3-M1 (ใหม่, medium) — `git rm -r -f --cached` ไม่ถูก gate**

untrack ไฟล์ออกจาก index โดยไม่แตะเนื้อหาไฟล์บนดิสก์ (`working_file_survives=true`,
`still_tracked=false` — พิสูจน์จริงแล้ว) ความเสียหายเบากว่า 3 ข้อบนตรงที่**ไม่ทำลายเนื้อหาไฟล์**
แต่เปลี่ยน tracked-state ของ repo แบบเงียบๆ ใต้ pane อื่น (commit ถัดไปของใครก็ตามจะเห็นไฟล์นี้เป็น
"deleted" ทั้งที่เนื้อหายังอยู่) — ไม่ critical เท่า H1-H3 แต่ควรพิจารณา gate เพิ่ม

หลักฐาน: `ART3/round3-results.json` case `B11-rm-rf-cached`

**R3-L1 (low, defense-in-depth) — `git reset --merge`/`--keep` ไม่ match pattern (เช็คแค่ `--hard`)**

`classify()` คืน `allowed=true` ทั้งคู่ (pattern เช็คเฉพาะ literal `--hard`) แต่พิสูจน์จริงแล้วว่า
**ไม่เสีย data จริง** ในเคสที่ทดสอบ — git เองมี safety net ในตัว: `--merge`/`--keep` จะ abort เอง
เมื่อไฟล์ที่ต่างกันระหว่าง HEAD กับ target commit มี uncommitted change ทับซ้อนอยู่ (รันจริงได้
`rc=128`, `error: Entry 'work.txt' not uptodate. Cannot merge.`, `uncommitted_lost=false` ทั้งคู่)
— ไฟล์ที่ไม่ต่างกันระหว่างสอง commit จะไม่ถูกแตะเลยด้วยดีไซน์ของ git เอง จึงไม่มี path ที่ทำให้
uncommitted work ของไฟล์ที่ไม่เกี่ยวข้องหายได้ ต่างจาก `--hard` ที่ไม่เช็คอะไรเลย — แนะนำให้เพิ่ม
เข้า pattern เพื่อความสม่ำเสมอ แต่ severity ต่ำเพราะพิสูจน์แล้วว่าใช้ทำลายข้อมูลจริงไม่ได้ในทางปฏิบัติ

หลักฐาน: `ART3/round3-results.json` case `B10a-reset-merge`, `B10b-reset-keep`

**ไม่พบ bypass จริงเพิ่มเติม (ปิดแล้ว/ไม่ใช่ช่องจริง):**

- `-c core.worktree=<x>` / `-c core.bare=false` (B1/B2): `_resolve_git_command_aliases()` ตั้ง
  `core_override=True` เมื่อเจอ `-c core.*` ซึ่งบังคับ `in_worktree=False` เสมอ — override นี้**เอา
  carve-out ออกได้เท่านั้น ไม่เคยให้เพิ่ม** (ทุก carve-out ในโค้ดต้องการ `in_worktree=True` จึงจะได้
  ข้อยกเว้น) จึงไม่มีทางใช้ `-c core.*` เพื่อ *ได้* สิทธิ์เพิ่มโดยโครงสร้าง ยืนยันด้วย B1 จริง: `-c
  core.worktree=<shared>` + `reset --hard` จาก cwd worktree ของตัวเอง → **DENY** เหมือนเดิม
- backslash `..\` เดิน -C ออกนอก worktree ตัวเอง (B4b, `git -C ..\ restore .`) → **DENY** ถูกต้อง —
  ยืนยันว่า fix รอบ 3b (`_resolve_relative_target` ต่อ cwd ก่อนเช็ค ownership) ครอบคลุม backslash
  ด้วย ไม่ใช่แค่ forward-slash
- `git stash push` (worktree ตัวเอง) ตามด้วย `git stash pop` เป็น**คำสั่งแยกกันคนละ call** (B7) →
  `pop` ยัง **DENY** เหมือนเดิมแม้เป็น session/context เดียวกันแต่คนละ Bash call — H1 fix (`pop`/
  `drop`/`clear`/`branch` เป็น Lead-only ไม่สนใจ worktree เลย) ไม่ได้พึ่ง state ข้าม call ใดๆ ที่จะรั่ว
- `git restore --source=HEAD --staged --worktree .` (B8) และ `git checkout -p` (B9) → ทั้งคู่ **DENY**
  เพราะ pattern `checkout`/`restore` เช็คแค่ subcommand token เฉยๆ ไม่สนใจ flag ต่อท้ายเลย ครอบคลุม
  อยู่แล้วโดยไม่ต้องแก้
- `git update-index --refresh` (B14, read-only control) → ยัง **ALLOW** ตามคาด ไม่มี over-block
  ใหม่เกิดขึ้นจากรอบนี้

**ไม่มีหลักฐานทำลายจริง (พิสูจน์ไม่ได้ในรอบนี้ ไม่ใช่ว่าปลอดภัยแน่นอน):**

- `%CD%\..` (cmd.exe, B5) / `$PWD/..` (bash, B6): `classify()` คืน `allowed=true` ทั้งคู่ เพราะ
  guard เห็นข้อความ `%CD%`/`$PWD` ตรงๆ (ไม่ expand) แต่**shell จริงจะ expand ก่อน git เห็นคำสั่ง** —
  รันจริงแล้ว shell expand ให้ `-C` ไปตกที่ `worktrees/proj/` (โฟลเดอร์ container ที่ไม่ใช่ repo เอง)
  แล้ว git เดิน parent lookup ขึ้นไปเจอ repo อื่นแทน ผลคือ `rc=1` (`pathspec '.' did not match`) —
  **ไม่เกิดความเสียหายจริงในเคสนี้** แต่เป็นเพราะโครงสร้างไดเรกทอรีทดสอบบังเอิญไม่มีไฟล์ตรงกัน ไม่ใช่
  เพราะ guard ป้องกันได้ — ช่องว่างเชิงสถาปัตยกรรมยังอยู่ (guard คำนวณ relative path จากข้อความดิบ
  ไม่เคย expand shell variable) แนะนำอย่างน้อยให้ปฏิบัติกับ target ที่มีเครื่องหมาย `%`/`$`
  แบบเดียวกับ "unresolvable" (เหมือน `-c core.*` ที่ parse ไม่ได้) คือปิด carve-out ทันทีแทนที่จะ
  ลองคำนวณ relative path จากข้อความที่มันไม่ได้ representถูกต้อง

**แนวแก้ที่แนะนำ:**
1. `_worktree_role_owns()` ต้อง resolve path จริง (`os.path.realpath`/`pathlib.Path.resolve()`,

   ข้อความ path ดิบ
2. เพิ่ม `apply` (ไม่ต้องแยก `-R` เพราะ apply ปกติก็ overwrite ได้เหมือนกัน) และ `read-tree` เข้า
   `_GIT_LEAD_ONLY_PATTERNS` กลุ่มเดียวกับ `checkout`/`restore` (ให้ worktree carve-out เดียวกันด้วย
   เพราะ blast radius เท่ากัน)
3. (medium, ไม่บล็อก ship ก็ได้) เพิ่ม `rm --cached`/`-r --cached` เข้า pattern เดียวกัน
4. (low, defense-in-depth) เพิ่ม `--merge`/`--keep` เข้า pattern เดียวกับ `--hard` ใน `reset`
5. (low, architectural) เมื่อ resolve relative `-C`/`--git-dir` target เจอ literal `%`/`$` ที่น่าจะ
   เป็น shell-variable reference ที่ parse ไม่ได้ ให้ปฏิบัติเหมือน unresolvable target (ปิด
   carve-out) แทนที่จะคำนวณ relative path จากข้อความนั้นตรงๆ
