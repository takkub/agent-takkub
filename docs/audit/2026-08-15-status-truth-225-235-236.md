# `takkub status` truth gap — #236 spinner-as-progress + permission dialog, #235 delivery/status contradiction, #225 pane-vanish-before-report

## #236 — pane ค้างที่ permission dialog 2h51m แต่ status บอก "working / last progress: 0s ago"

### Root cause (พิสูจน์จาก source, 2 กลไกแยกกัน)

**1. Progress clock นับ spinner frame เป็น progress จริง.**
`Orchestrator._compute_last_progress_ts` (orchestrator.py) signal #1 เดิมใช้ **raw transcript file
mtime** — bump ทุก PTY byte รวมถึง spinner animation (`Doing… (esc to cancel, 412s)`) และ
permission-dialog redraw เอง ทำให้ pane ที่ค้างอยู่กับที่ (ไม่มี progress จริง) ยัง update mtime
ต่อเนื่อง → `takkub status` อ่าน "last progress: 0s ago" ตลอดแม้ไม่มี output ใหม่จริง

Cockpit มีกลไกแก้ปัญหานี้อยู่แล้วสำหรับ watchdog อีกจุดหนึ่ง (`_check_stuck_panes`'s auto-recover,
"Bug-2 fix"): hash ของ screen content ที่ **filter spinner/counter line ออกก่อน**
(`_SPINNER_INTERRUPT_PHRASES` + `_SPINNER_VOLATILE_RE`) เก็บไว้ที่ `PaneState.last_content_change_ts`
อัปเดตทุก 5s tick — แต่ `_compute_last_progress_ts` (ที่ฟีด `takkub status`) เป็นคนละ code path ไม่เคย
อ่านค่านี้เลย เป็น 2 กลไกคู่ขนานที่ไม่คุยกัน

**2. ไม่มี detector สำหรับ Claude Code's own tool-permission approval dialog.**
`is_blocked_on_tty_prompt()` (pty_session.py) match แค่ pattern แบบ shell y/N ทั่วไป (`[y/N]`,
`(y/n)`, `overwrite?`, ...) — dialog ของ Claude Code เอง (`1. Yes` / `2. Yes, and don't ask again` /
`3. No … (esc)`) ไม่มี `[y/N]` bracket เลย ไม่ match pattern ไหนเลย และตัว footer ("esc to cancel")
ก็ถูกจัดเป็น hard-blocker (busy) อยู่แล้ว — pane เลยอ่านเป็น "กำลัง generate อยู่" ตลอดไป ไม่มี branch
ไหนจับสถานะ "ค้างรอ human กด" ได้เลย

### Fix

1. `_compute_last_progress_ts` — signal #1 เปลี่ยนไปอ่าน `PaneState.last_content_change_ts` (ตัวเดียว
   กับที่ `_check_stuck_panes` ดูแลอยู่แล้ว, spinner-filtered) ก่อน แล้วค่อย fallback ไป raw transcript
   mtime เฉพาะตอนที่ pane ยังไม่เคยผ่าน watchdog tick แรก (ไม่มี baseline)
2. เพิ่ม `PtySession.is_blocked_on_permission_prompt()` — anchor บน numbered option "1. Yes" +
   companion ("Esc to cancel" หรือ numbered "No") ในหน้าต่าง cursor-relative 12 แถว (คำถามของแต่ละ
   tool ต่างกัน — Bash: "do you want to proceed?", Edit: "do you want to make this edit to…?" —
   เลยไม่ยึดกับคำถาม ยึดกับโครงสร้าง option menu แทน ซึ่งคงที่ทุก tool)
3. ผูก detector ใหม่เข้ากับ **infra ที่มีอยู่แล้ว** แทนสร้างใหม่:
   - `lead_inbox._prompt_block_reason` — เพิ่ม "permission" reason (ก่อน "tty" catch-all)
   - `_check_idle_teammates`'s TTY-block suppression/surface path (#54) — เช็ค permission-prompt ก่อน
   - `_check_stale_markers` / `_check_proactive_compact` — ไม่ misfire ตอน pane ติด permission dialog
   - `_check_stuck_panes`'s TTY-block-defer-recovery (#54) — permission-dialog เข้าเงื่อนไข "defer
     recovery + surface to Lead" เดียวกับ tty prompt (ไม่ close→respawn ทับ conversation ที่กำลัง
     ทำงานอยู่)
   - `_maybe_surface_tty_block`/`_surface_tty_block_notice` รับ `kind="permission"|"tty"` เพื่อ wording
     ที่ถูกต้อง (ไม่บอกว่าเป็น "subprocess" ทั้งที่จริงเป็น dialog ของ CLI เอง)
4. `list_status_detailed`/`pane_status_report` เพิ่ม field ใหม่ `blocked_reason`
   (`None`/`"trust"`/`"permission"`/`"tty"`) — **ไม่แตะ `pane.state` เดิม** (additive reporting only,
   ไม่กระทบ `pane.state == "working"` check ที่มีอยู่ทุกจุด) — `takkub status` CLI render บรรทัด
   `⛔ blocked:<reason>-prompt` แยกจาก state ปกติ ให้ Lead เห็นตรงๆ ไม่ต้องเดา

### Multi-provider gap (ต้อง flag ตาม #103 — ไม่ปิดเงียบ)

`is_blocked_on_permission_prompt()` ยืนยันเฉพาะ wording ของ **Claude Code** เท่านั้น (เคสจริงที่เจอ)
codex/gemini-agy/opencode/kimi/cursor อาจมี tool-approval prompt คนละหน้าตา หรือไม่มีเลย — ยังไม่ได้
ตรวจสอบ/เพิ่ม pattern ให้ตอนนี้ เป็น known gap ที่ต้องเปิด issue แยกถ้าเจอ provider อื่นที่มีปัญหาเดียวกัน
(ไม่ auto-assume ว่า provider อื่นทำงานถูก)

### Test
`tests/test_orchestrator_stall.py` (3 ใหม่ ใน `TestComputeLastProgressTs` + 3 ใหม่ ใน
`TestListStatusDetailed`), `tests/test_pty_ready_prompt.py::TestIsBlockedOnPermissionPrompt` (7 ใหม่),
`tests/test_cli.py::TestPrintStatusReport` (2 ใหม่) — รวม `tests/test_idle_watchdog.py`,
`tests/test_stale_marker_detector.py`, `tests/test_stuck_recover.py`, `tests/test_lifecycle_recovery.py`,
`tests/test_update_splash_recovery.py`, `tests/test_delivery_blocked_prompt.py` ที่ต้องอัปเดต mock
fixture ให้ตั้งค่า `is_blocked_on_permission_prompt.return_value = None` (ไม่งั้น unconfigured
MagicMock คืนค่า truthy → misread ทุก pane ว่า blocked) — ทุกไฟล์ผ่านหมด

## #235 — delivery-busy-wait ขัดกับ status: สองแหล่งความจริงไม่ตรงกัน

### Root cause (พิสูจน์จาก source trace)

`_send_when_ready` (lead_inbox.py) ไม่มี guard กันการยิง 2 ครั้งซ้อนกันสำหรับ role เดียวกัน —
`DeliveryManager`'s single-flight gate (`begin_write`, keyed by `(project, pane, session_generation)`)
มีอยู่จริง แต่ทำงาน**เฉพาะหลัง `_deliver()` ถูกเรียกแล้วเท่านั้น** (ตอนสร้าง `delivery_id`) — ช่วง**ก่อน**
`_deliver()` (ตอน poll loop รอ pane ถึง ready prompt) ไม่มี dedup เลย

เคสจริง (saas_admin): assign ครั้งที่ 1 ถูก shell mangle แต่ยังไปถึง CLI (ข้อความ garbled) →
`_send_when_ready` #1 เริ่ม poll loop ของตัวเอง ครั้งที่ 2 (heredoc, ข้อความถูกต้อง) ยิง assign ใหม่
สำหรับ role เดิม → `_send_when_ready` #2 เริ่ม poll loop **อีกตัวหนึ่งคู่ขนาน** — ทั้งสอง loop รันเป็น
อิสระจากกัน pane ว่าง (ready) พอ #2 เจอ ready streak ครบ 5 วินาที ก็ deliver จริง (สอดคล้องกับที่
Lead เห็น `takkub status` = working, progress 0s ago) — แต่ loop #1 (garbled, ยังไม่ deliver เพราะ
ตอนเริ่ม poll ครั้งแรกยังไม่ถึง ready streak ครบ) เมื่อ pane เปลี่ยนเป็น busy (เพราะ #2 เพิ่ง deliver
จริง) loop #1 ก็เข้า branch "pane not ready → busy-wait extension" (#144) แล้วยิง
`[delivery-busy-wait] ... task ยังไม่ถึงมือ` เข้า Lead — ข้อความนี้เกี่ยวกับ attempt #1 (garbled, ถูก
ทิ้งไปแล้วโดยไม่มีใครบอก) แต่ Lead อ่านแล้วเข้าใจว่าเป็นเรื่องของ task ที่เพิ่งเห็นว่า deliver แล้ว —
สองแหล่งข้อมูล (status ที่ถูก vs. warning ที่ค้างจาก attempt เก่า) ขัดกันเอง

### Fix

`_send_when_ready` เพิ่ม **generation guard** ต่อ `(project, role)`:
- ทุกครั้งที่ถูกเรียก จะ claim generation ใหม่ล่าสุดทันที (`self._send_when_ready_generation[(project,
  role)] += 1`)
- ทุก poll (`_check()`) เช็คก่อนอื่นว่า generation ของตัวเองยังเป็นตัวล่าสุดอยู่ไหม — ถ้าไม่ใช่แล้ว (มี
  assign ใหม่มาแทนที่) **เงียบทันที** (`sent[0] = True`, log `task_deliver_superseded`, ไม่ paste,
  ไม่ warn Lead) — เพราะ delivery ใหม่กว่าคือ source of truth ตอนนี้ และจะรายงานสถานะของตัวเองเอง

ผลคือ: attempt เก่าที่ถูกแทนที่แล้วจะไม่มีทางส่ง warning ที่ขัดกับสถานะปัจจุบันของ pane อีก และลดความ
เสี่ยง resend ซ้ำที่ issue กังวลไว้ด้วย (attempt เก่าจะไม่มีทาง `_deliver()` เลยหลังถูก supersede)

**Scope ที่ตั้งใจไม่แตะ:** ประเด็นแยกที่ issue พูดถึง ("CLI ตอบ ok ทั้งที่ task ถูก shell mangle") —
issue ระบุเองว่า "อาจควรเป็น issue ต่างหาก" ไม่ได้แก้ในรอบนี้

### Test
`tests/test_delivery_supersede.py` (ใหม่ 3 เทส): stale loop ไม่ paste/ไม่ reschedule/ไม่ warn เมื่อถูก
supersede (รวมเคสที่ stale loop ไปถึง busy-wait branch ของตัวเองแล้วค่อยโดน supersede), sequential
(ไม่ overlap) ยังทำงานปกติไม่มี false-positive supersede event

## #225 — pane หายจาก `takkub list` ก่อน done report ถูกส่ง

### สถานะที่พบ: **ส่วนใหญ่ถูกแก้ไปแล้วโดย #163 (commit `4f0d214`, 2026-08-13 15:34) ก่อน #225 จะถูกล็อกอีก**

`git log --grep="#163"` เจอ commit ที่แก้ปัญหาเดียวกันนี้ตรงๆ อยู่แล้ว: `_has_pending_lead_notice` +
`_pending_notice_roles` ทำให้ `list_status`/`list_status_detailed` (แหล่งข้อมูลของ `takkub
list`/`status`) ยังโชว์ role ที่ pane ปิดไปแล้วแต่ done-notice ยังค้างอยู่ใน digest/live/durable queue
ต่อ (state = `Orchestrator._PENDING_NOTICE_STATE`) จนกว่า notice จะถูกส่งจริง — commit timestamp
(15:34) มาก่อน `#225` "created" timestamp (20:26 วันเดียวกัน, ตาม UTC+7) ตรงกับ pattern ที่เจอมาก่อน
(local-tracker → GitHub migration ให้ #167-183 มี stale duplicate — #225 เข้าข่ายเดียวกัน แม้จะไม่ได้
อยู่ในช่วงเลขที่ migrate ก็ตาม)

Audit doc เดิมของ #163 (`docs/audit/2026-08-13-cockpit-issues-163-165.md`) ระบุ **gap ที่เหลือไว้ชัดเจน
เป็น follow-up**: draft-hold branch ใน `_reap_pending_done_notices` (Lead มี unsubmitted text ค้างอยู่
ในกล่องพิมพ์) ไม่มี ceiling เลยโดยตั้งใจ (กัน regression ของ #118 ที่เคย force-flush ทับ draft จริงของ
user) — ตัดสินใจไว้แล้วว่าต้องออกแบบ safe delivery (post-Enter-verify แบบเดียวกับ `_pump_lead_notify`)
ก่อนถึงจะใส่ ceiling ได้อย่างปลอดภัย — scope ใหญ่กว่ารอบนี้ ไม่แตะซ้ำ

### Gap จริงที่พบเพิ่มและแก้ในรอบนี้: mobile `/api/activity` ไม่เคยได้ #163's fix

`remote/api.py::activity()` (พลัง mobile pulse page) อ่าน `orch._panes_by_project` **ตรงๆ** — ไม่ผ่าน
`list_status`/`list_status_detailed` เลย (คนละ code path จากที่ #163 แก้) — เป็น**อาการเดียวกับ #225
เป๊ะ**แต่เกิดบน mobile surface: role ที่เพิ่ง `done()` (pane auto-close ใน 2.5s) หายจาก mobile activity
feed ทันที ทั้งที่ report ยังไม่ถึง Lead จริง

### Fix
`activity()` เพิ่มการ merge `orch._pending_notice_roles(project_ns, known_states)` เข้ากับ role list —
โชว์เป็น entry แบบหยาบ `state: "idle"` (ไม่มี notice body, ไม่มี fine-grained detail — ตรงกับ DATA-MIN
contract ของ endpoint นี้ที่ประกาศไว้แล้วว่า "role + project + state + runtime only") ผลคือ role ที่
เพิ่ง finish ไม่หายจาก mobile feed ทันทีอีกต่อไป — gate ด้วย `PULSE_SHOW_TEAM` เดียวกับ role list ปกติ
(ปิด flag แล้วต้องไม่ leak การมีอยู่ของ role ผ่านทางนี้เหมือนกัน)

`pulse()` (legacy `/api/pulse`) ไม่ต้องแก้ — เรียกผ่าน `cmd:"list"` → `list_status_detailed` อยู่แล้ว
(#163 คุมให้แล้ว)

### Test
`tests/test_remote_api.py::TestActivity` (3 ใหม่): role ที่ pane ปิดแล้วแต่ notice pending ยังโชว์เป็น
idle, ถูกซ่อนตอน `PULSE_SHOW_TEAM=False`, ไม่ duplicate ถ้า role กลับมา live ก่อน notice ส่งเสร็จ
