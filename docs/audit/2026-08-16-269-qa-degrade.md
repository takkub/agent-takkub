# #269 (ครึ่งแรก) — qa ไม่ degrade เป็น claude เมื่อ provider auth fail

**สถานะ:** แก้แล้ว, targeted tests เขียว (158/158, ดูรายชื่อไฟล์ท้ายเอกสาร)
**Scope:** เฉพาะครึ่งแรกของ #269 (degrade path) — ครึ่งหลัง (`takkub list` โชว์ "working" ทั้งที่ pane ไม่เคยถึง ready) ตรวจแล้วว่า **#263 คุมเคสนี้อยู่แล้วจริง** ดูหัวข้อ "ครึ่งหลัง" ท้ายไฟล์

## อาการ

`qa` (provider gemini-agy ใน role-providers.json) auth fail ("not signed in") 3 รอบติด — Lead close+reassign ใหม่ 3 ครั้งได้ผลเหมือนเดิมทุกครั้ง ไม่เคย degrade เป็น claude substitute เลย ทั้งที่ `backend`/`frontend` ในเซสชันเดียวกัน degrade ได้ปกติเมื่อ spawn fail (no-content-retry → degrade → spawn สำเร็จ)

## Root cause (พิสูจน์จากโค้ด, ไม่ใช่การเดา)

ใน `lead_inbox.py::_send_when_ready`'s `_check()` closure มี **สอง path แยกกันโดยสิ้นเชิง** สำหรับ pane ที่ spawn แล้วใช้งานไม่ได้:

1. **no-content watchdog** (`pane.session.first_content_ts() is None` ค้างเกิน `NO_CONTENT_WATCHDOG_SEC`) — path เดียวที่เคยไปถึง `_recover_no_content_pane()` ซึ่งทำ close+respawn ครั้งแรกแบบไม่ degrade แล้ว **ครั้งที่สองค่อย degrade** (ตั้ง `PaneState.provider_override = "claude"`)
2. **auth-failure marker** (`pane.session.auth_failure_reason(provider)` ตรงกันติดกัน `_AUTH_FAILURE_CONFIRM_POLLS` (5) รอบ) — เดิมแค่ `_warn_lead_auth_failure()` แล้ว `_deliver(unconfirmed=True)` (blind-paste เข้า pane ที่พังอยู่) **ไม่เคยแตะ `provider_override`/`_recover_no_content_pane` เลย**

จุดที่ทำให้ path (1) ไม่มีวันครอบ path (2): `_first_content_ts` ใน `pty_session.py` ถูก stamp ทันทีที่ pyte เห็น **content chunk ที่ไม่ว่างชิ้นแรก** (`_feed_and_log`, บรรทัด ~1121-1126) — ข้อความ "not signed in" ของ gemini **คือ content** เอง ดังนั้น `first_content_ts()` จึงไม่มีวันเป็น `None` สำหรับ pane ที่ auth fail แบบมองเห็นได้ → `_no_content` check (บรรทัด ~1340-1346 เดิม) evaluate False เสมอ → `_recover_no_content_pane`/degrade mechanism ไม่มีวันถูกเรียกสำหรับเคสนี้

**นี่ไม่ใช่เรื่อง role-specific พิเศษ** — grep ทั้งไฟล์ไม่พบ guard ผูกกับชื่อ role ใดๆ (`qa`, ฯลฯ) ในเส้นทางนี้ ตัวแปรที่กำหนดพฤติกรรมคือ **ชนิดของ failure ที่ provider โชว์บนจอ** (มี text auth-error ที่จับได้ vs. ไม่มี output อะไรเลย) ล้วนๆ — backend/frontend ที่ observed degrade ได้เพราะ failure ของพวกมันเข้าเงื่อนไข "ไม่มี output เลย" ส่วน qa/gemini เข้าเงื่อนไข "มี output แต่เป็น auth error" ซึ่งไม่เคยมี degrade wiring มาก่อน

### สมมติฐานที่ตรวจแล้วและตัดทิ้ง
- ~~role ที่มี provider override ในไฟล์ config เดินคนละ path~~ — ตัด: ทั้งสอง path (`_check`'s auth-failure branch, `_derive_display_state`) resolve provider ผ่าน `getattr(pane.model, "provider_name", None) or "claude"` เหมือนกันหมด ไม่มีสาขาแยกตามว่าเป็น override หรือ default
- ~~qa มี guard พิเศษ (tiered scanning/model override)~~ — ตัด: grep `role_name == "qa"` และ pattern คล้ายกันทั่ว `lead_inbox.py` ไม่พบผลลัพธ์

## Fix

`lead_inbox.py`:
- `_check()`'s auth-failure branch เปลี่ยนจาก `_deliver(unconfirmed=True)` (blind-paste เข้า pane ที่พัง → เสียงานทิ้ง) เป็นเรียก `_recover_auth_failed_pane(...)` ใหม่
- Extract กลไก close+respawn(+degrade) ที่ใช้ร่วมกันออกเป็น `_recover_broken_pane(..., degrade, kind)` — ทั้ง `_recover_no_content_pane` (no-content watchdog, เดิม) และ `_recover_auth_failed_pane` (auth-failure, ใหม่) เรียกใช้ตัวเดียวกัน แทนที่จะก็อปโค้ด close/respawn/`provider_override` ซ้ำ
- **auth-failure degrade ทันทีตั้งแต่ครั้งแรก** (ไม่มี retry แบบไม่ degrade ก่อนเหมือน no-content) — เพราะ auth failure เป็นสัญญาณที่ชัดเจนว่า provider ใช้ไม่ได้ ณ ตอนนี้ (login wall ไม่หายเองจากการ retry provider เดิม, ตรงกับที่ Lead ลอง manual reassign 3 ครั้งแล้วผลเหมือนเดิมทุกครั้งในรายงาน) — reuse provider เดิมอีกรอบเสียเวลาเปล่า
- เพิ่ม `_warn_lead_auth_failure_degrade()` แจ้ง Lead รอบสอง (ต่อจาก `_warn_lead_auth_failure()` เดิมที่บอก reason/login-hint) ว่ากำลัง degrade เป็น claude แล้ว spawn ใหม่ — pattern เดียวกับ `_warn_lead_no_content(degrade=True)`

`spawn_engine.py`: อัปเดต docstring ของ `PaneState.provider_override`/`no_content_recover_attempts` ให้ตรงกับความจริงใหม่ (ใช้ร่วมกันสองเส้นทาง ไม่ใช่ no-content อย่างเดียว) — ไม่แตะ logic ของ `spawn()` เพราะมันอ่านแค่ field เหล่านี้ ไม่สนใจว่าใครเป็นคนตั้ง

## ผลลัพธ์หลังแก้

- auth-failure ของ provider ใดก็ตาม (ไม่ว่า role จะใช้ default provider หรือ override) → degrade เป็น claude แล้ว respawn ใหม่ เหมือน no-content path — พิสูจน์ผ่าน `test_auth_failure_degrade.py::TestCheckRoutesAuthFailureToDegrade` (สองเทส: role มี provider override แบบ `gemini-agy`, กับ role ใช้ default `claude`) — ทั้งคู่เดิน code path เดียวกัน ไม่มีเคสไหนได้ path พิเศษ
- ready-prompt-wins + consecutive-poll-confirm (จาก #256/#257) **ไม่ถูกแตะ** — เพิ่มแค่ `sent[0] = True` (สอดคล้อง pattern ที่จุดอื่นในไฟล์เดียวกันทำอยู่แล้วก่อน early-return) และเปลี่ยน action หลัง confirm จาก blind-deliver เป็น recover; ยืนยันด้วย `test_delivery_auth_failure.py` (12 เทสเดิม, แก้แค่ 2 จุดที่ assert blind-write ให้ assert degrade-call แทน — ไม่แตะ assertion ของ detection logic เอง) ทั้งหมดเขียว

## ครึ่งหลัง — `takkub list` โชว์ "working" ทั้งที่ pane ไม่เคยถึง ready

**ยืนยันแล้วว่า #263 คุมเคสนี้จริง** — `orchestrator.py::_derive_display_state` (บรรทัด ~4389-4444) priority tier 1 คือ `login-required`:

```python
provider = getattr(pane.model, "provider_name", None) or "claude"
auth_reason = session.auth_failure_reason(provider)
if auth_reason:
    return "login-required"
```

ตรวจ **ก่อน** tier อื่นทั้งหมด (booting/waiting-delivery/busy/unknown) และ override ค่า raw `"state"` ("working"/"active") ที่ orchestrator เผื่อ optimistically ตั้งไว้ — ใช้ provider resolution แบบเดียวกับที่ `_check()` ใช้ (`pane.model.provider_name`, ไม่ hardcode) จึงครอบทั้ง role ที่ใช้ default provider และ role ที่มี provider override (เช่น qa → gemini-agy) เหมือนกัน `takkub list`/`status` render จาก `display_state` นี้ ไม่ใช่ raw `state` แล้ว จึงไม่ขัดแย้งกับ delivery-unconfirmed warning อีกต่อไป — **ไม่ต้องแก้เพิ่ม**
