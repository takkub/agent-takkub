# #262 / #258 / #259 / #265 — `takkub wait` and repaste-delivery fixes

Branch: `wt/backend-1786847166`. All 4 issues sit in the same layer
(`lead_wait.py` / `lead_inbox.py` / `orchestrator.py`'s inbox-notice
plumbing) — done together per Lead's instruction so they don't clash.

## #262 — `wait` resolved with a stale done event while the pane was still working

**Root cause (proven by reading, not guessed).** `_resolve_role_wait_status`'s
freshness fast-path compared a role's `_wait_done_events` entry only against
the *wait registration's* `started_ts`:

```python
fresh = event is not None and event.get("ts", 0.0) >= started_ts
```

A registration stays open as long as **any** watched role is still pending —
its `roles` list never shrinks as individual roles resolve, and `started_ts`
is fixed at whenever `begin_wait` first created it (and is **not** advanced
when a new role is unioned in via the attach path). So if Lead reassigns a
role that already finished — or attaches a role that already finished — to a
brand-new task *while the registration is still open* (e.g. still waiting on
a sibling role), the stale event from the task *before* this one still
satisfies `event.ts >= started_ts` (started_ts predates both tasks) and gets
returned as `"done"` immediately, without ever consulting the role's actual
current pane state or its own `assign_ts`.

This reproduces the reported symptom exactly: `wait` printed `done: backend,
devops` while `takkub list` showed both panes `working` and no new report
file existed on disk.

**Fix.** Floor the freshness threshold at `PaneState.assign_ts` too — the
same signal the adjacent terminal-state carve-out (`covers_active_assign`,
added for #249) already trusted:

```python
effective_start = max(started_ts, assign_ts)
fresh = event is not None and event.get("ts", 0.0) >= effective_start
```

`assign_ts` is stamped fresh by `_assign_dispatch` on every new assign
regardless of registration/attach timing, so it closes both manifestations
of the bug (mid-wait reassignment on an already-open registration, and
attach-with-already-reassigned-role) with one change. The terminal-state
branch's own `pane_state`/`assign_ts` lookup was hoisted to the top of the
function and reused instead of being computed twice.

Deliberately **not** changed: per-role `started_ts` tracking on attach. Once
freshness is floored at `assign_ts`, the registration-level `started_ts`
alone is sufficient — a stale event can never predate the role's own current
assignment either way.

Tests: `tests/test_lead_wait.py::TestPollWaitStaleEventVsCurrentAssign` (3
cases — mid-open-registration reassignment, attach-after-reassignment, and a
guard against over-correction: a genuinely fresh completion must still
resolve normally).

## #258 — repaste bypassed the cancel validator

**Root cause.** `_delayed_enter_verified`'s own QTimer chain (CR resend at
what's now `lead_inbox.py:~583`, payload repaste at `~713`) wrote via
`_safe_session_write` with `delivery_id`/`session_generation`/`expires_at`
but **no `validator`** — only the caller's very first write (before the
chain was ever scheduled) attached
`validator=lambda: manager.validate_for_write(...)`. `_WriterThread.run`
(pty_session.py) only drops a message if `message.cancelled`, its
`expires_at` has passed, its `session_generation` is stale, **or**
`message.validator()` returns `False` — with no validator attached, a
delivery cancelled by `takkub send`/`takkub task cancel` (#255) after the
chain was already scheduled still landed its repaste on the composer,
defeating the exact protection #255 added.

**Fix.** `_delayed_enter_verified` now accepts a `validator` parameter and
forwards the *same* one to both internal `_safe_session_write` calls (CR and
repaste). The one real production call site (`lead_inbox.py`'s task-delivery
`_deliver()`) now passes the identical closure the original write used. The
other two call sites (`_pump_lead_notify` / `_force_deliver_done_notices`,
Lead-inbox delivery — not backed by a `DeliveryManager` delivery, `payload`
is always `None` there so the repaste branch never fires) are unchanged —
out of scope, nothing to cancel.

Tests: `tests/test_fan_out_delivery_race.py::TestRepasteCarriesTheCancelValidator`
— one asserts both the CR and repaste writes carry the validator kwarg; the
other drives a fake writer that mimics `_WriterThread`'s own validator gate
and proves a cancel landing mid-chain (between the CR firing and the
repaste's verify tick) keeps the payload off the simulated PTY.

## #259 — `wait` deaf to delivery-health notices, including a wider gap than reported

**Root cause, part 1 (as reported).** `Orchestrator._pending_notice_outside`
deliberately skips roles in `watched_roles` — correct for done/FAILED
(those resolve via `_wait_done_events`), but `[delivery-unconfirmed]` /
`[spawn-stuck]` / `[delivery-boot-stall]` / `[spawn-failed]` notices never
call `done()`/`failed()`, so a watched role stuck in one of these states had
nothing to resolve it short of the full `--timeout`.

**Root cause, part 2 (found while investigating, not in the original
report).** These 4 markers are authored by the orchestrator itself
(`_warn_lead_*`), not by a teammate's `done()` call, so they don't carry the
`[role done]`/`[role FAILED]` shape `_notice_role_tag` parses — they read
`⚠️ [delivery-unconfirmed] {role_name} pane ...` instead. `_notice_role_tag`
returns `None` for these bodies, so `inbox_report` falls back to
`item_role = "system"` for every one of them, and the **old**
`_pending_notice_outside` skipped `role == "system"` *before* the
blocking-marker check ever ran. That means these 4 notice kinds were
invisible to `_pending_notice_outside` for **every** role, watched or not —
proven by the fact that the existing #253 tests only ever exercised
`[role FAILED]`-tagged bodies, never one of these 4 markers.

**Fix.**
1. `lead_inbox.py`: new `_system_marker_role(body)` regex-extracts the
   target role from these 4 markers' plain-text shape. Deliberately kept
   separate from `_notice_role_tag` — that function's output feeds
   `_provenance_stale`'s pane_token verification (#228) for genuine
   `done()`-authored bodies; widening it would add an untested code path
   for no benefit, since these system notices never carry a `pane_token`.
2. `_pending_notice_outside` now falls back to `_system_marker_role` when
   `inbox_report` tagged an item `"system"`, fixing the outside-role gap
   too (not just the reported watched-role one).
3. New `Orchestrator._pending_system_notice_for_watched(project_ns,
   pending_roles)` — mirrors `_pending_notice_outside` but for roles
   *inside* the watched set, restricted to the 4 system markers only (not
   the broader `_is_blocking_lead_notice`, since a watched role's own
   FAILED already resolves via `_wait_done_events` — checking it here too
   would be redundant).
4. `poll_wait` calls this second check only when the first (`_pending_notice_outside`)
   found nothing and something is still pending.

Tests: `tests/test_lead_wait.py::TestPollWaitInterruptForWatchedRole` (5
cases: delivery-unconfirmed/spawn-stuck for a watched role interrupt;
delivery-boot-stall for an *outside* role now interrupts too, proving part 2
of the fix; a watched role's own FAILED still resolves normally, not as an
interrupt; an unrelated digest line naming the role doesn't interrupt).

## #265 — `wait` deaf to the pane owner's own new input

**Root cause.** `poll_wait`'s only interrupt source was
`_pending_notice_outside` (#253) — nothing watched for the Lead pane's
*owner* typing a new command while `wait` was blocking. Whatever they typed
sat as queued CLI stdin, unprocessed, until `wait` returned (up to the
30-minute cap).

**Signal used.** `Orchestrator._on_pane_input` already feeds every Lead-pane
keystroke into `_track_lead_draft_input` (issue #3's draft-typing guard) —
and, per that method's own comment, **only** real keystrokes reach it:
engine-originated writes (`_notify_lead`, `_pump_lead_notify`, task pastes)
go straight to `session.write()` and never pass through `_on_pane_input`.
That structurally rules out the false-positive the task called out (a
cockpit-authored notice/task paste must never be mistaken for the owner
interrupting) — no new capture path was needed.

One gap in reusing `_lead_draft_state` directly: it resets to
`state=EMPTY, pending_since=0.0` the instant Enter submits a line (see
`advance_draft_state`'s `_ENTER_BYTES` branch), so it can't answer "did the
owner submit something a moment ago" — only "is a draft currently held".
Added a second, minimal piece of state fed from the *same* choke point:
`Orchestrator._lead_last_user_input_ts: dict[project_ns, float]`, stamped in
`_on_pane_input` right next to the existing `_track_lead_draft_input` call,
and — unlike the draft tracker — never cleared. This answers "did the owner
type *anything* (submitted or not) after this wait started watching",
matching the issue's explicit decision that a still-unsubmitted draft should
count too (it already proves the owner is about to act).

**Fix.**
1. `Orchestrator.__init__`: `self._lead_last_user_input_ts: dict[str, float] = {}`.
2. `Orchestrator._on_pane_input`: stamps it alongside `_track_lead_draft_input`.
3. `LeadWaitMixin._pending_user_input_interrupt(project_ns, started_ts)`:
   returns `{"role": LEAD.name, "detail": "...", "reason": "user_input"}`
   when the timestamp postdates the wait's `started_ts`, else `None`.
4. `poll_wait` checks this last (after the two notice-based checks), only
   while something is still pending — same gating discipline as #253/#259.
5. `cli.cmd_wait` special-cases `interrupt.get("reason") == "user_input"`
   with a distinct Thai message ("คุณพิมพ์ข้อความใหม่เข้ามาระหว่างรอ...")
   instead of the role-report wording ("[role] needs attention...") which
   would be misleading here (there's no teammate role to look up).

The existing `interrupt` dict shape for #253/#259 (`{"role", "detail"}`, no
`"reason"` key) is unchanged — old exact-dict-equality tests still pass
since `"reason"` is only ever added by the new user-input path.
