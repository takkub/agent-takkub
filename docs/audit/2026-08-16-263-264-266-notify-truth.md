## #264 — done reports delayed up to a minute by a fixed digest window

**Root cause.** `_INBOX_DIGEST_WINDOW_MS` (60s) applied in full to every
digestible notice (`[role done]` / peer-CC), even a solo `done()` with no
other role in the project still working — nothing could ever join that
"burst", but it paid the full window's tax anyway. Combined with the
ready-gate busy-retry (~30s) and draft-hold chain already documented in the
module, a clean report could take up to ~2 minutes to actually reach Lead's
pane — matching the user's own description: "รู้สึกเหมือนค้างรออะไรบางอย่าง
ตลอด".

**Fix.**
1. `_INBOX_DIGEST_WINDOW_MS`: 60s → 15s (top of the issue's own suggested
   10-15s range, not the bottom — a genuine parallel fan-out's completion
   spread under load can be several seconds, and 15s still cuts the
   worst-case 4x while keeping more margin for that spread than 10s would).
2. New `_INBOX_DIGEST_ADAPTIVE_SETTLE_MS` (3s): used INSTEAD of the full
   window whenever `Orchestrator._other_roles_still_active(project_ns,
   exclude_role)` — read straight from `list_status`, so it can never
   disagree with what `takkub list` shows — finds no other role in a
   non-terminal state. Re-evaluated on **every** notice added to a burst
   (each one re-arms `_arm_lead_digest`'s generation-checked timer), so a
   genuine multi-role burst still gets the full window right up until its
   LAST item, at which point nothing is left to wait for and that final
   re-arm switches to the short settle.
3. `exclude_role` matters because `done()` calls `_notify_lead` **before**
   flipping its own pane to `"done"` (the notice must exist before the
   state transition that would otherwise make it look terminal) — without
   excluding the reporting role by name, a solo completion would always
   see its own still-"working" pane as "another active role" and never get
   the short window.

**Deliberately out of scope:** item 3 of the issue (expose this in
Settings without needing to know the env var name) — that's
`settings_dialog.py`, reserved for codex's parallel #260 work per this
task's own file-exclusion list. `TAKKUB_INBOX_DIGEST_MS` remains the only
way to override the base window; the adaptive settle isn't
env-configurable (it's a fixed 3s — a knob nobody asked for yet).

Tests: `tests/test_adaptive_digest_window.py` (solo → short window; burst
still forming → full window; last item in a burst switches to short;
reporting role's own pane correctly excluded; explicit smaller configured
window still wins over the adaptive one). One pre-existing test in
`tests/test_lead_inbox_digest.py`
(`test_default_window_debounces_burst_and_renders_single_digest`) had its
fixture updated to register a genuinely-still-working sibling role — it was
asserting the OLD "solo notice still gets the full window" behavior, which
is exactly what #264 intentionally changes; updated to keep testing what
it's actually named for (burst debounce/combine mechanics) rather than
re-testing the bug. `tests/test_pending_done_notice_visibility.py`'s
`TestDoneCloseRacesDigestDelivery` test had a hardcoded `ms == 60_000`
assertion updated to the adaptive constant for the same reason — the race
it proves (pane gone from the registry before its digest fires) still
holds since the 3s settle is still longer than the pane's 2.5s auto-close.

## #266 — stale notices presented as current state

**Root cause.** Two independent gaps, both stemming from the same pattern:
a notice is built once, at the moment its underlying condition is
DETECTED, then can sit in the digest window / live queue / durable store
(#264's chain — busy-retry ~30s, draft-hold, then the reaper's
`_DONE_NOTICE_STALE_S` 60s escalation) for minutes before it's actually
pasted, with nothing re-checking whether the condition still held:

1. **No occurrence timestamp on most notices.** Only the done-digest path
   (`_format_digest_item`, #241) ever rendered a `[HH:MM:SS · age]` stamp.
   `_enqueue_live_lead_notice`'s own docstring claimed "the live queue
   delivers promptly enough that staleness isn't a concern" — #266's own
   evidence (a `[delivery-unconfirmed]` notice arriving after its pane had
   already closed) disproves that.
2. **No re-validation of re-checkable claims.** A "task may not have
   landed" system notice (spawn-failed / delivery-unconfirmed / spawn-stuck
   / delivery-boot-stall / delivery-busy-wait — the same class
   `_system_marker_role` recognises, #259) makes a claim about a specific
   role's pane that's trivially re-checkable against the pane registry at
   flush time, but nothing did.

**Fix.**
1. `_occurred_stamp(queued_ts, now_ts)` — extracted from
   `_format_digest_item`'s existing stamp logic into a shared helper.
   `_notify_lead` gained a `queued_ts` parameter (defaulting to `time.time()`)
   threaded through to `_enqueue_live_lead_notice` (now a 3-tuple
   `(body, pane_token, queued_ts)`, matching the digest queue's shape) and
   every `_pending_done_notices` dict creation/spill site. Every durable
   round-trip (`_flush_pending_done_notices` re-routing through
   `_notify_lead`) passes the ORIGINAL timestamp through explicitly —
   without that, each requeue hop would reset "when did this happen" to
   "whenever it got reprocessed", defeating the whole point. Both live-queue
   delivery paths (`_pump_lead_notify`, `_force_deliver_done_notices`) now
   prefix the body with this stamp right before writing.
2. `_revalidate_system_notice(project_ns, body)` — for the 5 markers only
   (everything else, including plain done/CC/FAILED bodies, passes through
   byte-for-byte unchanged): looks up the target role's CURRENT state via
   `list_status`; if the pane has since reached a terminal state or no
   longer exists, prefixes the body with a "✅ [คลี่คลายแล้ว — ... ภาพ ณ
   ตอนเกิดเหตุ ไม่ใช่สถานะปัจจุบัน]" banner instead of dropping it — Lead
   may still want the history, just not mistake it for the present. Applied
   at both delivery-flush call sites, right before write.
3. `_system_marker_role`'s regex extended to also recognise
   `[delivery-busy-wait]` (#144) — it wasn't in the original 4-marker set
   at all, so evidence item 3 (a busy-wait notice for an already-closed
   kimi pane) was previously invisible to any role-attribution logic.

**Deliberately out of scope (documented, not silently dropped):** two of
the issue's 5 evidence items don't have a cheap synchronous re-check
available:
- The worktree-uncommitted warning (`_check_uncommitted_async` /
  `_uncommitted_warning`) — re-validating it for real means re-running
  `git status --porcelain` (another async QProcess call) at flush time,
  which changes control flow significantly (the notice would need to be
  rebuilt asynchronously rather than flushed synchronously in that tick).
  Gets the universal timestamp treatment only — Lead can see it's N minutes
  old and judge for themselves, but the claim itself isn't re-verified.
- `[{role} closing] N subprocess(es) about to be killed` — describes an
  imminent, already-decided action (`terminate()` runs right after), not
  an ongoing state that could resolve itself before flush. Timestamp-only
  is the correct fix here, not re-validate/drop, since the event genuinely
  did happen.

Follow-up if wanted: a real re-validation hook for the worktree-dirty case
would need `_check_uncommitted_async` (or an equivalent synchronous `git
status`) re-run from inside `_revalidate_system_notice` or a sibling
function, gated the same way, before delivery.

Tests: `tests/test_notice_revalidation.py` (11 cases: `_occurred_stamp`
formatting; delivery-unconfirmed/busy-wait flagged resolved when the target
pane has closed by flush time vs. not flagged when still active; plain
done/FAILED notices never revalidated; a live blocking notice carries a
clock stamp; a durable→live requeue preserves the ORIGINAL occurrence time
instead of resetting it; both guarantees re-proven through
`_force_deliver_done_notices`, the reaper's separate delivery path).

## #263 — pane state has 3 disagreeing sources of truth (partial, scoped fix)

**The issue's ask is genuinely three separate things**, and only one of
them was safe to touch in this pass:

1. Unify `pane.state` (orchestrator-declared at dispatch) / the ready
   marker (screen-scraped, provider-calibrated) / the progress clock into
   one state with clear priority — **not attempted**. This means
   re-deriving `pane.state` itself from ready-marker behaviour, which lives
   in `provider_spec.py` and the pty_section ready-marker fixture table —
   **explicitly reserved for gemini's parallel #256/#257 work** per this
   task's own instructions ("ห้ามแตะ provider_spec.py และตาราง
   ready-marker fixture"). Touching it here risks exactly the kind of
   cross-provider regression those issues exist to prevent, on a shared
   surface two panes were editing concurrently.
2. Distinguish "login-required" (the kimi evidence — screen shows
   `Model: not set, send /login to login`) as its own state — **not
   attempted**, for the same reason: detecting it requires
   provider-specific screen-scraping, i.e. `provider_spec.py`/ready-rule
   territory.
3. Fix "active" vs. the screen genuinely showing "Working" (the codex
   evidence) and the permanently-stuck "last progress: unknown" for
   codex/kimi/opencode — **not attempted**, same reason: both are ready-
   marker/content-clock calibration issues per-provider.

**What WAS safe and is fixed:** the gemini evidence (`takkub list` showed
"working" from minute one while the screen was stuck on "Signing in..."
and the task had never actually been pasted in — the cockpit's own
`[delivery-unconfirmed]` notice was sitting there unread at the same
moment) is a DIFFERENT, narrower bug: `pane.state` is an
orchestrator-declared optimistic label stamped at dispatch time ("task
assigned = working"), never cross-checked against the delivery layer's own
knowledge of whether the paste actually landed — and that delivery-health
signal already exists as a queued notice, addressable without touching any
provider-specific code at all.

**Fix:** `list_status_detailed` gained an additive `delivery_unconfirmed:
bool` field per role. `Orchestrator._role_delivery_unconfirmed(project_ns,
role)` is True when a "task may not have landed" notice
(`_BLOCKING_NOTICE_MARKERS` — spawn-failed/delivery-unconfirmed/spawn-stuck/
delivery-boot-stall; deliberately NOT delivery-busy-wait, which means
delivery DID land and the pane is just slow) is currently queued for that
specific role. `pane.state`/the `"state"` string itself is left completely
untouched — every existing `pane.state == "working"` check and every
existing `list_status`/`list_status_detailed`-string comparison elsewhere
is unaffected; this is purely an additional key Lead (or `takkub
status`/any future CLI rendering) can read alongside the existing state.

**A real bug found and fixed while building this**: the first
implementation reused `inbox_report()` to scan for the matching notice —
that method's documented side effect is fingerprinting every body it
returns into `_inbox_seen` (so a LATER `takkub inbox` pull collapses a
digest line the reader already saw, #241). Since `list_status_detailed`
runs on every `takkub status`/`takkub list` call — far more often and far
more incidentally than an explicit `takkub inbox` pull — this silently
marked every currently-queued digest notice as "already read" the moment
Lead so much as checked status, so it would render collapsed
("อ่านแล้วผ่าน takkub inbox") once it actually flushed, even though Lead
never explicitly read it. Caught by
`test_checking_status_does_not_mark_the_notice_as_read` before landing.
Fixed by scanning the 3 raw queues directly (the same shape
`_has_pending_lead_notice` already reads) instead of going through
`inbox_report`.

**Recommended follow-up** (not attempted here — flagging per the task's own
instruction to report what's left rather than force it): items 1-2-3 above
need whoever owns the ready-marker/provider-calibration layer (per
`docs/architecture/godfile-map.md`'s hidden edges into `provider_spec.py`)
to design the actual state-priority unification and the login-required/
booting detection, ideally alongside #256/#257 rather than as a third
concurrent editor of that surface.

Tests: `tests/test_delivery_unconfirmed_status_flag.py` (6 cases: flag true
when a matching notice is queued; false with nothing queued; false for a
DIFFERENT role's notice — no cross-role leakage; delivery-busy-wait
deliberately does NOT set this flag, unlike #266's broader revalidation set;
flag stays false for a non-"working" pane; and the regression guard for the
`inbox_report` fingerprinting bug above).
