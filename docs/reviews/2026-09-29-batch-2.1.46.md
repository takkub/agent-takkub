# Batch 2.1.46 Review — 2026-09-29

**Verdict: NOT RELEASABLE.** One blocker prevents every spec/budget confirmation from succeeding, and the task token counter can stop ordinary work early. The backlog handoff also loses identity when same-role assignments overlap.

## 1. D — spec confirmation and Qt threading: FAIL

**BLOCKER — [orchestrator.py:2746](../../src/agent_takkub/orchestrator.py#L2746).** `_confirm_task_discipline()` calls `self.receivers(signal.signal.encode("utf-8"))`. On this PyQt6 runtime, `QObject.receivers()` accepts the bound `pyqtBoundSignal`, not its bytes/string signature. The call raises `TypeError`, which the surrounding `except Exception` converts to `False` before `signal.emit()` runs. I connected a real Qt receiver (`receivers(bound_signal) == 1`) and called the method; it still returned `False`. As a result, business-rule assigns are always denied even when the user would accept, and any capped-task resume is also denied. No headless fallback can fix this; it needs the signal API call corrected first.

With a valid receiver, the intended worker-thread flow is sound in structure: emitting from the IPC worker queues the UI slot, and only that worker waits on the event. A same-thread call can use Qt's direct connection/modal nested loop. **Headless/remote with no receiver currently fails closed**; that is safe for the confirmation boundary, but remote business-rule assignment has no confirmation path and should remain an explicit unsupported workflow unless a remote user confirmation is added.

**MED — [work_discipline.py:21](../../src/agent_takkub/work_discipline.py#L21), [work_discipline.py:48](../../src/agent_takkub/work_discipline.py#L48).** The detector gates across the whole task text if it finds any business-domain word and any surviving number. It returned `True` for `runtime/fix-655512b2-r1.md` and `runtime/fix-token-cap.md`, both developer fix instructions that discuss the detector/token accounting and include numeric examples. It returned `False` for `runtime/task-655512b2.md`, `runtime/fix-762-r1.md`, `runtime/fix-763-764.md`, `runtime/fix-82a5bb37-r1.md`, `runtime/fix-worktree-reuse.md`, and this review brief. In the token-cap fix text, generic `total` is treated as a business domain, so technical token totals satisfy the gate. This remains a false-positive path for maintenance tasks that quote business examples or talk about totals.

## 2. D — task budget and Ctrl+C: FAIL

**HIGH — [orchestrator.py:14201](../../src/agent_takkub/orchestrator.py#L14201).** `last_turn_end_ts` is part of the usage deduplication marker. When usage is sampled before the stop hook updates that timestamp, the same provider usage snapshot is added again on the next watchdog tick even though `total/input/output/model` have not changed. I invoked the actual watchdog with a fixed `current_usage()` snapshot of 1,000 tokens, then changed only `last_turn_end_ts`; the counter moved from 1,000 to 2,000 and halted a task with a 1,500-token cap, writing `\x03`. Codex's meter reports the most recent turn's usage, so the turn-end timestamp change can double-count a single turn and prematurely interrupt normal work.

**MED — [orchestrator.py:14214](../../src/agent_takkub/orchestrator.py#L14214).** The watchdog sets `task_budget_halted` before sending Ctrl+C and ignores the return value from `session.write()`. A rejected/failed write is not retried because subsequent watchdog ticks skip halted tasks. In that case, the task may keep running past the cap while the owner is told it stopped. The state remains `working` until the provider screen reports an idle/ready state, so status can lag the budget notice as well.

The default limits are tiny/normal/deep = 50k/200k/500k. The targeted tests verify a single usage sample and a single interrupt, but do not cover a stop-hook timestamp change or a failed write. This also does not conflict with #762's independent fix-loop attempt ceiling; it is a separate task-time/token stop.
