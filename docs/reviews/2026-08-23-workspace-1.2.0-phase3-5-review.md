**Verdict: MERGE-WITH-FIX** — one must-fix (cross-project trust-boundary bypass in the
`preview`/`design` IPC layer), everything else is should/nit. The file-editing core (phase 3:
containment, atomic write, conflict detection) is solid and well-tested; the preview/design
*policy* functions (phase 5) are correct in isolation, but the IPC layer that calls them does not
authenticate which project a caller is allowed to act on.

## Findings

### 1. [MUST-FIX] `preview`/`design` IPC trusts a caller-supplied `from_project` — breaks project isolation

**Files:** `cli_server.py:367-479` (`_dispatch`), `orchestrator.py:6074-6180`
(`preview_command`/`design_publish`/`design_approve`/`design_revise`), confirmed intentional by
`tests/test_workspace_preview_design_cli.py:217-226` (`test_no_token_required`) and
`:188-199` (`test_status_round_trip`, dispatches with a bare `from_project` field, no `auth`).

`cli_server._dispatch`'s Layer 4 pane-token gate (`cli_server.py:441`) derives `from_project`
from the server-side `_pane_tokens` registry — trustworthy — but only for
`("done", "progress", "send", "answer-picker", "hook", "session-report")`. `preview` and `design`
are **not** in that list, so for them `from_project = req.get("from_project")` (line 374) flows
straight through, unauthenticated, into `Orchestrator.preview_command`/`design_publish`/
`design_approve`/`design_revise` as the `project` argument. `_resolve_project` (`orchestrator.py:
1551`) only validates the string isn't a path-traversal name (`validate_name`) — it does not
check that the caller actually belongs to that project.

`cli.py`'s own `_with_project` (`cli.py:292-297`) stamps `from_project` from `TAKKUB_PROJECT`, an
env var set once at pane spawn — trivially overridden by anything running in that pane's shell
(`TAKKUB_PROJECT=other-project takkub preview open-file --path x.html`), or bypassed entirely by
talking to the TCP socket directly with a hand-built JSON payload, exactly the "confused teammate
pane" scenario `_dispatch`'s Layer 1 comment (`cli_server.py:379-381`) already worries about for
lifecycle commands.

**Impact — a pane/process belonging to project A can, by naming project B in the request:**
- `preview open-file`: read any `.html`/`.htm` file under **project B's** configured roots
  (`approved_artifact_roots` resolves purely from `projects.json[project_B].paths`) and have it
  rendered in B's shared Preview widget — cross-project file-content disclosure, gated only by
  extension, not by ownership.
- `preview open-url`: force project B's Preview to navigate to an arbitrary loopback URL —
  UI-level cross-project disruption.
- `design publish`: write a fabricated `draft` artifact record into **project B's**
  `design_artifacts.jsonl` with an attacker-chosen title/kind, and (for `mode="html"`) exercise
  the same cross-project file read as above.
- `design approve`/`design revise`: flip status on an existing artifact **in project B** and
  trigger `_notify_lead` (`orchestrator.py:6155-6160`, `:6174-6179`) — a real, convincing-looking
  message injected into **project B's Lead pane** ("✅ [design] artifact ... approved") that B's
  Lead did not actually approve.

**Why this is a real regression, not an accepted trust-local pattern:** the code comment at
`orchestrator.py:6065-6072` justifies this as sitting at the same "trust-local, scoped by
from_project" tier as `list`/`ram-status`/`performance-status` — but those are **read-only,
low-sensitivity pane-status queries**. `preview`/`design` do file reads scoped to another
project's roots *and* durable writes (artifact registry, Lead notification) — the exact category
this codebase already gates behind pane-token identity for `done`/`progress`/`send`. Multi-project
isolation is a first-class concern elsewhere in this repo (see project memory
`only-touch-our-own-repo.md`); this IPC path lets one project's pane act as any other configured
project without a token.

**Suggested fix (Lead to route):** add `"preview"` and `"design"` to the pane-token-derived
identity gate at `cli_server.py:441` (same shape as `send`/`done`) so `from_project` for these two
commands comes from the server's own `_pane_tokens` registry, not the request body — mirroring
exactly what already happens for `send`. `status`/read-only actions could stay trust-local if
Lead decides that's an acceptable exception, but `open-url`/`open-file`/`close`/`publish`/
`approve`/`revise` should not trust caller-supplied project identity for a state-changing action.

### 2. [SHOULD] `save_atomic`/`_write_atomic_text` don't bound the size of text being *written*

**File:** `editor_service.py:197-239`, `_write_atomic_text:168-194`.

Read-side size capping is solid (`stat_snapshot` gates on `st.st_size` before ever reading full
file content — `editor_service.py:107,111`). But `save_atomic(path, text, ...)` writes whatever
`text` the caller passes with no upper bound. In production `text` originates from Monaco's
buffer for a file that was ≤2MB on open, so this doesn't trigger in the normal UI flow — but the
JS→Python bridge slot `saveFile(path, text)` (`editor_widget.py:411-413`,
`static/editor/index.html:305`) accepts an arbitrary-length string from the page's JS context with
no server-side check. Given the module's own stated principle ("every path here goes through
`resolve_and_contain`" — never trust the JS side blindly), the same defense-in-depth should apply
to size: reject (or truncate-and-flag) a save whose `len(text.encode())` exceeds `max_bytes` (or
some generous multiple) before calling `_write_atomic_text`, rather than writing an unbounded
string to disk unconditionally.

### 3. [SHOULD] `EditorHost.run_js`'s inline-JS string construction relies on `json.dumps` default `ensure_ascii=True` — undocumented, easy to break in a future edit

**File:** `editor_widget.py:604-786` (every `run_js(f"...{json.dumps(...)}...")` call site).

`json.dumps(str)` with default `ensure_ascii=True` \u-escapes everything non-ASCII, including
U+2028/U+2029 (LINE SEPARATOR/PARAGRAPH SEPARATOR) — characters that are valid inside a JSON
string but, pre-ES2019, are illegal unescaped inside a JS string literal and would otherwise
silently truncate/corrupt a `runJavaScript` call carrying file content containing them. This
currently works correctly *only* because nobody passed `ensure_ascii=False`. That's a fragile
invariant to leave undocumented — a future contributor "optimizing" these calls (e.g. switching to
`ensure_ascii=False` for smaller payloads, since these can carry up to 2MB of file text over the
bridge) would reintroduce a script-corruption bug with no test currently guarding it. Not
independently exploitable today (Python string escaping still prevents a quote/backslash
breakout regardless of `ensure_ascii`), but worth either a one-line comment pinning the
requirement, or an explicit `json.dumps(text, ensure_ascii=True)` at each of these call sites so
the invariant is visible at the point that matters instead of relying on the default.

### 4. [SHOULD] `navigation_allowed`'s file-mode contract is not yet exercised by any real navigation event, and its comparison shape isn't obviously compatible with what a `QWebEngineView` will report

**File:** `preview_controller.py:199-217`.

Per the master plan (§4, phase 5 row), `preview_widget.py` doesn't exist yet, so
`navigation_allowed` is currently a policy function with no caller. That's expected for this
phase's scope — flagging as a **contract requirement for the widget that lands on top of this**,
not a bug in what's here today:

- The widget **must** call `navigation_allowed` from `QWebEnginePage.acceptNavigationRequest` (or
  equivalent) for *every* navigation, including a server-side HTTP redirect the loopback dev
  server issues after `open_url` — a redirect is itself a navigation Chromium will ask the host
  page about, and if the widget doesn't intercept it, a `http://127.0.0.1:3000` target could
  redirect to an arbitrary external origin without ever consulting this policy. `is_loopback_url`
  is only checked once, at `open_url` time.
- File mode's `target_url == current.target` (`preview_controller.py:211`) compares against
  `current.target`, which is a plain resolved filesystem path string (`str(resolved)` —
  `preview_controller.py:161`), not a URL. A real in-page navigation event from Qt will report a
  `file://`-scheme `QUrl`. Unless the widget normalizes the incoming target to the same bare-path
  string form before calling this function, *every* same-file anchor-jump navigation will be
  wrongly rejected (fail-closed, so not a security bug, but will read as "the preview is broken"
  during phase-5 widget development if this mismatch isn't caught first).

Recommend making both of these explicit acceptance criteria in whatever phase-5 widget PR follows,
since `preview_controller.py` itself can't enforce either from outside a real `QWebEnginePage`.

### 5. [NIT] `_on_changes_changed` builds a CHANGES-row path without `resolve_and_contain`, relying on git's own path semantics for safety

**File:** `project_explorer.py:284-290`.

```python
row.setData(0, _PATH_ROLE, str((repo_root / change.path).resolve()))
```

`change.path` comes from `git status --porcelain=v2` output (`git_changes_service.py`), which is
always repo-root-relative and can't contain `..`/absolute segments for a well-formed git working
tree — so this isn't currently exploitable, and both downstream consumers
(`_on_context_menu` at `project_explorer.py:318` and `EditorHost.open_file` → `read_file_for_editor`
at `editor_widget.py:130`) do re-validate via `resolve_and_contain` before any filesystem touch.
Still, every other path constructed in this module goes through the containment gate as a matter
of house style (per the module's own docstring: "Every path this module hands back has already
passed `resolve_and_contain`"); this is the one exception. Worth a one-line
`resolve_and_contain(repo_root / change.path, roots)` here too, purely for consistency with that
stated invariant — not because there's a known bypass through it.

## What's solid (verified, not just read)

- **Path confinement (checklist item 1):** `resolve_and_contain` (`project_file_index.py:68-78`)
  is the single gate, called consistently by every FS-touching code path in phase 3 (open, save,
  diff, reload, reveal, open-externally) and phase 5 (`resolve_preview_file`). The phase-1 NTFS
  junction fix (per-entry re-verification in `list_dir_sync`, not just `is_symlink()`-flagged
  entries — `project_file_index.py:157-170`) is still in place. Bridge-received paths
  (`saveFile`/`keepMineSave`/`requestDiff`/`reloadFromDisk`/`askAgent`) are never trusted directly
  for identity — `EditorHost` looks up `project_name` from its own server-side `_open_paths` dict
  (populated only by Python at open time), so a compromised/buggy editor-page JS context can only
  ever act on a path that was already opened through a containment-checked flow — confirmed by
  reading `editor_widget.py:689-698`, `:716-731`.
- **`save_atomic` conflict rule (item 2):** mtime_ns+size+sha256, server-tracked baseline
  (`EditorHost._file_states`, never updated by a disk-watch echo — `editor_widget.py:788-791`),
  same-directory temp + `os.replace`, BOM/newline preservation verified against
  `test_editor_service.py`'s CRLF/BOM/Thai-path/symlink-escape cases. `[Keep mine]` re-snapshots
  disk immediately before writing rather than trusting the stale conflict-time state
  (`editor_widget.py:326-334`). Binary/too-large gated **before** a full read
  (`editor_service.py:97-131`, size determined from `stat()` only).
- **QWebChannel bridge (item 3):** `static/editor/index.html` loads only
  `qrc:///qtwebchannel/qwebchannel.js` and a local `vendor/` script — no CDN, no remote origin ever
  gets this bridge. No `innerHTML`/`insertAdjacentHTML` use anywhere in the page's JS; all
  untrusted content (file text, filenames) goes through `.textContent`/Monaco model APIs. Every
  exposed `@pyqtSlot` (`_EditorBridge`, `editor_widget.py:389-425`) only emits a Qt signal —
  no slot performs a filesystem action inline without going through the same containment-checked
  worker path.
- **Preview loopback gate (item 4):** `is_loopback_url` correctly restricts to http(s) +
  `127.0.0.0/8`/`::1`/literal `localhost`, checked against the literal hostname string (no DNS
  resolution, so no rebinding window) — verified against `test_preview_controller.py`'s
  accept/reject parametrized cases. `javascript:`/`file:` schemes are rejected outright by the
  scheme allowlist.
- **Ask Agent bound (item 5):** selection text is capped at 4000 chars both client-side
  (`static/editor/index.html:713`) and again defensively in `main_window._on_editor_ask_agent`
  (`main_window.py:487`) — confirmed both call sites exist and both actually slice to `[:4000]`.
  No secret/env var is ever interpolated into a bridge call, a design-artifact record, or a
  `_log_event` payload in any of the reviewed modules.
- **Concurrency/IO (item 6):** every git subprocess call (`project_file_index.py`,
  `git_changes_service.py`, `editor_widget.py`) sets `timeout=`, `creationflags=SUBPROCESS_NO_WINDOW`,
  and explicit `encoding="utf-8", errors="replace"` (not locale-default — matters for Thai
  filenames on cp874 Windows). All FS/git work runs on `QThreadPool` workers, never the Qt main
  thread; `FileWatchService`'s `fileChanged` signal handler only queues a debounced flush
  (`_DEBOUNCE_MS=400`), the actual stat+hash happens in `_SnapshotWorker.run`.
- **Fail-safe (item 7):** every worker-thread signal emit goes through a `_safe_emit` wrapper that
  swallows `RuntimeError` from a torn-down receiver (consistent pattern across all four modules).
  Every `project_roots(...)` lookup in `editor_widget.py` is wrapped in a defensive
  `except Exception` (malformed `projects.json` never crashes a bridge callback). Missing Monaco
  bundle degrades to a read-only `<pre>` viewer via an `onerror`/4s-timeout fallback
  (`static/editor/index.html:242-262`), matching the ADR's documented phase-2 behavior.
