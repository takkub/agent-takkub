# ใบงานและการแก้ซ้ำของ Lead

ใช้กับ `takkub assign` ทุก role/provider; งานเล็กย่อได้แต่ต้องมีผลลัพธ์และวิธีตรวจ. ระบบส่งกติกาการทำงานและรูปแบบรายงานเดียวกันให้ pane ตอน spawn.

## ก่อน assign

- **ผลลัพธ์:** อาการหรือเป้าหมายที่ผู้ใช้ขอ และเกณฑ์ที่เห็นได้ว่าจบ
- **หลักฐาน:** ขั้นตอน/คำสั่งที่ทำให้เกิด, log หรือ path ที่ Lead ตรวจแล้ว; แยกข้อเท็จจริงกับสมมติฐาน
- **ขอบเขต:** cwd, ไฟล์/subsystem ที่เกี่ยว, สิ่งที่ห้ามแตะ, งานที่ต้องรอ
- **การตรวจ:** วิธีเล็กที่สุดที่พิสูจน์พฤติกรรมจริง พร้อม OS/provider ที่เกี่ยวข้อง
- **การส่งต่อ:** รายงาน STATUS, CHANGED, EVIDENCE และ REMAINING ตาม context ของ pane

ส่งข้อสรุปที่ Lead ตรวจแล้วลงใบงาน ไม่ให้ pane อ่านไฟล์เดิมซ้ำโดยไม่จำเป็น. อย่าใช้คำสั่งลอยๆ เช่น "แก้ให้ผ่าน" หรือชื่อ issue อย่างเดียว.

## เมื่อผลตรวจล้มเหลว

1. แนบอาการล่าสุด สิ่งที่ลองแล้ว ผลแต่ละรอบ และ test/repro เดิมในใบงานใหม่
2. ถ้าหลักฐานยังไม่พอ สั่งเก็บข้อมูลที่แยกสมมติฐานได้ก่อนแตะโค้ด
3. ระบุว่าแนวทางรอบใหม่ต่างจากรอบก่อนอย่างไร; ตรวจ failure เดิมก่อนขยาย scope
4. หลังอาการเดิมไม่ดีขึ้นสองรอบ ให้หยุด assign อัตโนมัติเรื่องเดิม สรุปสิ่งที่รู้/ยังไม่รู้และทางเลือกแก่ผู้ใช้; เปลี่ยน provider ต้องส่งประวัติเก่าตามไปด้วย

ระบบบังคับเพดาน fix-loop แล้ว: tiny/normal หยุดก่อน assign เมื่อ failure signature เดิมถึงเพดาน และต้องให้ผู้ใช้ยืนยันพร้อมเหตุผลผ่าน `--ack-ceiling` ก่อนข้ามเพดาน ประวัติผูกกับงานและเดินทางข้าม role/provider ได้ ดูรายละเอียด/ข้อยกเว้นใน `docs/lead/fix-loop.md`.

## สรุปถึงผู้ใช้

ผลลัพธ์ก่อน (เสร็จ / ยังไม่เสร็จ / ติดอะไร) → หลักฐานที่ตรวจจริง → สิ่งค้างและขั้นตอนถัดไป. การแก้ไฟล์หรือ test ผ่านเพียงอย่างเดียวไม่พิสูจน์ผลลัพธ์ที่ผู้ใช้ขอ.
